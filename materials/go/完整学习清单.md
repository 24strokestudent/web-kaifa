# Go 后端从零到项目：C++ 学习者的完整路线与练习清单

**对象**：有 C++ 算法和基础语法经验，但没系统学面向对象、没学 Go 或后端。**方法**：把语言知识立即用在 HTTP 与数据库项目中。

- 每天建议：25 分钟读、75 分钟写、25 分钟测、15 分钟复盘；按个人进度灵活延长。
- **真实标准**：能解释数据流、能修改、能处理错误输入、能自己测试；不是只看过教程。

## 2. 详细知识清单（含要点和易错点）

### M01 环境、工具链与程序入口
- 阶段：语言 / 第 1 周 / 必学 / 约 2h
- **本章目标**：能独立创建 Go 模块、运行、格式化、构建和排查最基本的环境问题。

- **Go 安装与 PATH**：去 go.dev/dl 安装当前受支持的稳定版，终端执行 go version；Windows 推荐 PowerShell + VS Code Go 扩展。  
  - ⚠️ 易错：装了 Go 但旧终端找不到 go，先重开终端并确认 PATH。
- **package main 与 main()**：可执行程序必须属于 main 包并包含 func main()；import 是引入包，不是 C++ 的 #include 文本复制。  
  - ⚠️ 易错：同目录不同 .go 文件不能随意声明成不同包。
- **go mod init**：在项目根目录执行 go mod init example/go-practice；go.mod 说明模块路径与所需 Go 版本。  
  - ⚠️ 易错：不要把 go.mod 当成源代码，更不要每建一个文件都初始化一次模块。
- **go run、go build**：go run . 直接编译并运行；go build ./... 构建所有包；go run main.go 可能漏掉同包其他源文件。  
  - ⚠️ 易错：项目有多个 .go 文件时优先用 go run .。
- **gofmt、go test、go vet**：go fmt ./... 自动格式化，go test ./... 运行测试，go vet ./... 做静态检查。  
  - ⚠️ 易错：格式统一是 Go 的常规工程约定，不是选修美化。

**掌握验收**：
- [ ] 能解释 package 与 module 的区别
- [ ] 能说出 go run . 和 go build ./... 的用途
- [ ] 能运行 go fmt ./...
- [ ] 能新建并提交 Git 仓库

**练习**：在 Windows 新建 go-lab 项目，打印姓名、今天的学习目标，再修改输出并重新运行。
**通过标准**：截图或文本记录 go version、go run . 的输出；提交包含 go.mod、main.go、README.md 的第一个 commit。

### M02 基础语法与控制流
- 阶段：语言 / 第 1 周 / 必学 / 约 3h
- **本章目标**：利用 C++ 的已有基础快速迁移，不再背诵你已经懂的循环和条件思想。

- **变量与短声明**：var n int = 3、n := 3、const pi = 3.14；:= 仅能在函数内部声明变量。  
  - ⚠️ 易错：Go 编译器通常不允许局部变量声明后未使用。
- **类型与显式转换**：int、int64、float64、bool、string；数值类型不同通常需要显式转换，例如 int64(n)。  
  - ⚠️ 易错：不要假设 Go 自动完成 C++ 风格的数值混用。
- **零值**：数字是 0、bool 是 false、string 是空串、指针/slice/map/interface 等有 nil 零值。  
  - ⚠️ 易错：nil map 可读取但不能直接写入。
- **if 与作用域**：if err := do(); err != nil { ... } 支持判断前的短语句，变量只在该 if 相关作用域有效。  
  - ⚠️ 易错：if 后没有小括号，左大括号必须与条件处于同一行。
- **只有 for**：for i := 0; i < n; i++、for condition、for { } 三种常见模式；没有 while 关键字。  
  - ⚠️ 易错：不能像 C++ 写 ++i 作为表达式；++ 是语句。
- **switch**：可省略表达式，case 默认不会自动 fallthrough；适合替代多级 if。  
  - ⚠️ 易错：与 C++ switch 默认穿透行为不同。
- **函数、多返回值**：func div(a,b int) (int,error) 可以同时返回结果和错误；Go 没有常规函数重载。  
  - ⚠️ 易错：不要忽略返回的 err，也不要用 panic 替代正常错误处理。

**掌握验收**：
- [ ] 能写循环和 switch
- [ ] 能看懂 := 与 var
- [ ] 能解释零值
- [ ] 能自己写返回 (int,error) 的函数
- [ ] 能完成 3 道简单 C++→Go 改写

**练习**：写一个命令行成绩统计器：输入若干分数，计算最小值、最大值、平均值，非法分数返回错误。
**通过标准**：至少测试空输入、正常输入、负数、超过 100 的分数四种情况。

### M03 slice、map 与字符串
- 阶段：语言 / 第 1 周 / 必学 / 约 3h
- **本章目标**：能用 Go 的主要容器代替 vector、unordered_map，避免常见的 nil 和复制陷阱。

- **数组与 slice**：[3]int 是长度属于类型的一部分的数组；[]int 是动态切片，具有 len/cap，底层引用数组。  
  - ⚠️ 易错：slice 赋值和切片可能共享底层数据，修改一处影响另一处。
- **append 与扩容**：s=append(s,x) 返回新的 slice 值，扩容时可能搬迁底层数组。  
  - ⚠️ 易错：不能只调用 append(s,x) 却丢掉返回值。
- **make 与 nil**：make([]int,0,10)、make(map[string]int) 用来初始化 slice/map；nil slice 可以 append。  
  - ⚠️ 易错：nil map 不能赋值，nil slice 与空 slice 序列化 JSON 时可能不同。
- **map 读写**：m[k]=v；v,ok:=m[k] 判断是否存在；range map 遍历顺序不保证稳定。  
  - ⚠️ 易错：不能把 map 的随机遍历顺序用作分页或稳定输出。
- **range 的语义**：for i,v := range xs 遍历的是每轮元素值；直接改 v 不会修改 slice 中的原元素。  
  - ⚠️ 易错：更新元素请用 xs[i] = ...。
- **string、byte、rune**：Go 字符串存 UTF-8 字节序列；len("中") 是 3，[]rune("中") 长度为 1。  
  - ⚠️ 易错：处理中文字符个数不能直接用 len(string)。
- **排序与常用库**：slices.Sort、sort.Slice、strings、strconv 是常见工具；记住搜索文档而非硬背所有 API。  
  - ⚠️ 易错：不要把字符串字典序误当数值顺序。

**掌握验收**：
- [ ] 能初始化 map 并统计频率
- [ ] 能解释 len 与 cap
- [ ] 能区分 byte/rune
- [ ] 能理解 slice 共享底层数据
- [ ] 能给结果稳定排序

**练习**：单词频率排行：从一行文本提取单词，忽略大小写，输出次数前 3 的单词；同次数按字典序排序。
**通过标准**：测试重复词、空文本、并列次数，排序结果每次运行一致。

### M04 struct、方法、指针、接口
- 阶段：语言 / 第 1 周 / 必学 / 约 3.5h
- **本章目标**：无需先学传统 OOP：掌握数据结构、方法、组合以及小接口就能开始开发。

- **struct 组织数据**：type Problem struct { ID int64; Title string } 将字段组织在一起，类似 C++ struct。  
  - ⚠️ 易错：Go struct 不等于 class；没有类继承和传统构造函数强制机制。
- **方法 receiver**：func (p Problem) IsSolved() bool 是绑定到命名类型的方法；可以给自定义类型添加行为。  
  - ⚠️ 易错：只有 receiver 参数不同通常不构成重载。
- **值接收者与指针接收者**：func (p *Problem) MarkSolved() 会修改原对象；值接收者拿到一份副本。  
  - ⚠️ 易错：想改结构体字段但用了值接收者会导致原值没变化。
- **指针与 nil**：&p 取地址，*p 解引用；Go 有垃圾回收，无需用 new/delete 管理普通对象生命周期。  
  - ⚠️ 易错：不要解引用 nil 指针；不必一见指针就想到 C++ 的手动释放。
- **导出规则**：跨包访问的标识符首字母大写，如 Problem、Title；小写只在包内可见。  
  - ⚠️ 易错：json 编码一般只处理可导出的字段；小写字段即使写了 json tag 也不生效。
- **interface 隐式实现**：type Store interface { Save(Problem) error }；实现了所需方法的类型即满足接口，无需 implements。  
  - ⚠️ 易错：不要一开始给每个结构体都抽象一个接口；让需求决定接口。
- **组合优先**：struct 可以嵌入其他字段或类型，用组合复用数据/行为；不要把 C++ 继承层级直接搬到 Go。  
  - ⚠️ 易错：接口表示行为契约，不代表继承树。

**掌握验收**：
- [ ] 能定义 Problem
- [ ] 能写修改状态的指针方法
- [ ] 能解释 Go 为何不需要传统 class
- [ ] 能写一个简单 Store 接口
- [ ] 能解释大写字段的含义

**练习**：实现 Problem{ID,Title,Solved} 与 MarkSolved()；写一个按标题关键字筛选 []Problem 的函数。
**通过标准**：调用方法后原对象真的改变；输出 JSON 含正确字段；能演示值接收者与指针接收者的区别。

### M05 error、defer、JSON、I/O
- 阶段：语言 / 第 1 周 / 必学 / 约 3h
- **本章目标**：学会后端最常碰到的错误传播和请求 JSON 解析。

- **error 是值**：函数返回 (T,error)，约定 err==nil 表示没有错误；用 if err != nil 尽早返回。  
  - ⚠️ 易错：不要用 panic 处理用户输入不合法等预期情况。
- **包装与识别错误**：fmt.Errorf("load problem: %w",err) 保留错误链；errors.Is(err,sql.ErrNoRows) 判断类别。  
  - ⚠️ 易错：仅拼接字符串会丢失可识别的错误链。
- **defer**：defer rows.Close() 表示函数返回时执行清理；常用于文件、响应体与数据库游标。  
  - ⚠️ 易错：defer 的执行时机是当前函数返回，不是当前 if 块结束。
- **JSON struct tag**：`json:"title"` 控制字段名，`omitempty` 可以省略适用的空值字段。  
  - ⚠️ 易错：导出字段、JSON 标签和请求结构需对应；不能只靠标签导出私有字段。
- **Encoder/Decoder**：json.NewEncoder(w).Encode(value)，json.NewDecoder(r.Body).Decode(&input)；编码错误和写响应顺序都要处理。  
  - ⚠️ 易错：不要在写状态码之前已向响应写入数据，否则状态码可能固定为 200。
- **输入尺寸与格式校验**：限制请求体字节数，检查类型、长度、必填项，并识别多余 JSON 数据；适时使用 DisallowUnknownFields。  
  - ⚠️ 易错：解析成功不代表业务有效，例如 title 仍可能是空串。

**掌握验收**：
- [ ] 会写 if err != nil
- [ ] 会用 defer 关闭资源
- [ ] 能 JSON 编解码
- [ ] 能限制/校验用户输入
- [ ] 能区分 panic 和 error

**练习**：读取题目 JSON，拒绝空标题、过长标题、无法解析的 JSON，返回结构化错误结果。
**通过标准**：验证字段缺失、未知字段、错误字段类型、过大 Body、额外 JSON 文档。

### M06 包管理、测试入门和命令
- 阶段：语言 / 第 1 周 / 必学 / 约 2h
- **本章目标**：理解 Go 项目的构成和开发时必须会用的 6 条命令。

- **包与模块的层次**：目录通常是一个 package；module 可包含多个 package，go.mod 声明依赖图与模块路径。  
  - ⚠️ 易错：不要从绝对 Windows 路径 import 本地 Go 文件。
- **import 循环依赖**：Go 不允许包互相 import 构成环；把共同类型移到合适包或重新划分职责。  
  - ⚠️ 易错：不要为绕开循环依赖而建几十个空目录。
- **go mod tidy**：整理实际导入依赖；go.sum 保存模块校验信息，应正常提交版本控制。  
  - ⚠️ 易错：不要随意删除 go.sum 来“修复”依赖。
- **gofmt 与惯例**：Go 项目统一 gofmt，命名偏短、可读，错误及时返回。  
  - ⚠️ 易错：不要机械套用 C++ 复杂命名和宏体系。
- **小测试先行**：使用 *_test.go、func TestXxx(t *testing.T)，运行 go test ./...；先测纯函数最容易上手。  
  - ⚠️ 易错：测试是否通过不等于需求正确；断言必须对照独立的预期。

**掌握验收**：
- [ ] 知道 package 与 module 的界限
- [ ] 会用 go mod tidy
- [ ] 会运行 go test ./...
- [ ] 会自己写 2 个单元测试

**练习**：把成绩统计器拆成 calc 包和 main 包，为平均值函数写 4 个测试。
**通过标准**：编译无循环依赖；所有测试通过，并故意修改实现使至少一个测试失败。

### M07 Web 基础：一次请求发生了什么
- 阶段：网络 / 第 1～2 周 / 必学 / 约 3h
- **本章目标**：理解浏览器、客户端、服务器、TCP/HTTP、URL 和 JSON 的分工。

- **前端与后端**：浏览器负责界面，后端接收请求、执行业务规则、读写数据、生成响应；API 是双方的契约。  
  - ⚠️ 易错：浏览器看到 JSON 不代表“没有后端”，恰好可能是 API 成功返回。
- **URL 结构**：协议、主机、端口、路径、查询参数；例如 http://localhost:8080/problems?page=2。  
  - ⚠️ 易错：Query 参数与 JSON Body 是不同位置，不可混淆。
- **HTTP 方法**：GET 读取、POST 创建/触发、PATCH 局部修改、PUT 通常整体替换、DELETE 删除；应遵循预期语义。  
  - ⚠️ 易错：GET 不应偷偷修改数据；重复提交 POST 的影响要考虑。
- **状态码**：200 成功、201 创建、204 无内容、400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突、500 服务端异常。  
  - ⚠️ 易错：400 和 500 不可一概混用；401 与 403 有明确区别。
- **Header、Body、Content-Type**：Content-Type: application/json 声明消息体格式，Authorization 用于携带授权凭据。  
  - ⚠️ 易错：不能靠 URL 参数传密码和长期密钥。
- **JSON 数据协议**：对象、数组、布尔、数字、null；后端输入输出用稳定字段与约定好的错误结构。  
  - ⚠️ 易错：数字字符串 "2" 与 JSON 数字 2 不是一种类型。

**掌握验收**：
- [ ] 能画出请求链路
- [ ] 能解释 GET 与 POST 的区别
- [ ] 能给常见错误匹配状态码
- [ ] 能区分 URL Query 与 JSON Body

**练习**：不用框架，先用浏览器和 curl/PowerShell Invoke-RestMethod 查看两个公开测试接口的响应头和 JSON。
**通过标准**：能说出请求方法、URL、状态码、响应体各自是什么；能解释 404 与 500 的区别。

### M08 net/http 与路由处理
- 阶段：网络 / 第 1～2 周 / 必学 / 约 3.5h
- **本章目标**：只用标准库就能写出真正可访问的 Go HTTP API。

- **ServeMux 与 Handler**：http.NewServeMux() 注册路由，处理函数签名为 func(http.ResponseWriter,*http.Request)。  
  - ⚠️ 易错：ResponseWriter 是输出通道，Request 是输入，不要反着理解。
- **路由模式与 PathValue**：Go 1.22+ 支持 "GET /problems/{id}"，用 r.PathValue("id") 取路径参数。  
  - ⚠️ 易错：GET 方式路由也匹配 HEAD；需要理解协议行为。
- **Query 与表单**：r.URL.Query().Get("page") 取查询参数；字符串需 strconv.Atoi 转换并检查 err。  
  - ⚠️ 易错：查询参数可能缺失、重复或不是整数。
- **Body 解码**：通过 json.NewDecoder(r.Body).Decode(&req) 接收 JSON，设置请求大小限制并校验输入。  
  - ⚠️ 易错：只解析不校验容易造成脏数据甚至过大请求。
- **写状态码和 JSON**：先设置 Header，再 WriteHeader，再写 Body；无特殊情况 Encoder.Encode。  
  - ⚠️ 易错：先 Write 了响应体，再改状态码通常已经无效。
- **HTTP 服务器设置**：http.Server 可配置 ReadHeaderTimeout、ReadTimeout、WriteTimeout；初学部署也应避免无约束超时。  
  - ⚠️ 易错：http.ListenAndServe 的最简示例适合本地学习，公网服务还需要更多保护。
- **调用工具**：curl -i、curl.exe -i 与 PowerShell Invoke-RestMethod 都能测接口；Windows PowerShell 的 curl 别名可能指向 Invoke-WebRequest。  
  - ⚠️ 易错：不要把 PowerShell curl 别名行为当成标准 curl 的参数规则。

**掌握验收**：
- [ ] 能启动 :8080
- [ ] 能注册路由
- [ ] 能读取 path/query/body
- [ ] 能按状态码返回 JSON
- [ ] 能用 curl.exe 或 PowerShell 测试

**练习**：实现 GET /health、GET /hello?name=、GET /add?a=3&b=5。
**通过标准**：合法参数得到 JSON，缺失或非法数字得到 400；用命令行至少测试各 2 个场景。

### M09 REST API、CRUD 与校验
- 阶段：网络 / 第 2 周 / 必学 / 约 4h
- **本章目标**：独立设计和实现内存版刷题记录 API，掌握真实业务接口的最小闭环。

- **资源建模**：把 Problem 看作资源：ID、platform、title、difficulty、solved、created_at。  
  - ⚠️ 易错：不要把每个操作都写成 /doAddProblem 这样的随意路径。
- **CRUD 端点**：GET /problems、GET /problems/{id}、POST /problems、PATCH /problems/{id}、DELETE /problems/{id}。  
  - ⚠️ 易错：GET 列表与 GET 单条的响应形状需清楚区分。
- **请求 DTO 与领域对象**：CreateProblemRequest 不应该由用户指定数据库生成的 ID；响应 DTO 可以屏蔽敏感字段。  
  - ⚠️ 易错：直接绑定数据库模型到请求体容易暴露不该由客户端更改的字段。
- **输入验证**：标题不为空且长度受限，difficulty 在允许值集合内，ID 是正整数。  
  - ⚠️ 易错：错误值不要悄悄当成默认值，除非 API 明确约定。
- **统一错误响应**：例如 {"error":{"code":"INVALID_INPUT","message":"title required"}}，便于前端处理。  
  - ⚠️ 易错：错误时不应返回 200，也不要把数据库密码泄漏到客户端。
- **内存存储并发安全**：map 放在服务进程里时可用 sync.RWMutex 保护读写；未来切换数据库后可移除此层数据竞争风险。  
  - ⚠️ 易错：http.Server 会并发处理请求，裸写全局 map 会引发数据竞争。

- [ ] 能列出每个端点的请求和响应
- [ ] 能返回 400/404/201
- [ ] 共享 map 有锁保护
- [ ] 能生成可复现请求示例

**练习**：完成刷题管理器内存版，支持添加、分页获取、查看、修改 solved、删除。
**通过标准**：每个操作均有成功和失败案例；重新启动数据会丢失——能解释这正是下一步使用数据库的原因。

### M10 SQL 与关系数据库
- 阶段：数据库 / 第 2 周 / 必学 / 约 4h
- **本章目标**：不依赖 ORM，自己能设计表、写 SQL 并理解数据约束。

- **表、行、列与主键**：用 problems 表存题目；id BIGINT GENERATED ... AS IDENTITY PRIMARY KEY。  
  - ⚠️ 易错：主键用于唯一识别，不是业务排名。
- **数据类型与 NULL**：TEXT、BOOLEAN、TIMESTAMPTZ、BIGINT；NULL 表示未知或不存在，不等于空串或 0。  
  - ⚠️ 易错：错误使用 NULL 可能引发扫描和过滤的意外。
- **INSERT、SELECT、UPDATE、DELETE**：掌握增删改查及 WHERE；更新和删除务必限制目标行。  
  - ⚠️ 易错：忘记 WHERE 可能更新/删除整张表。
- **WHERE、ORDER BY、LIMIT/OFFSET**：按 solved 过滤、按 id 稳定排序、分页；OFFSET 对大数据量会变慢。  
  - ⚠️ 易错：不写 ORDER BY 的查询行顺序没有保证。
- **约束**：NOT NULL、UNIQUE、CHECK、FOREIGN KEY 用于保护数据完整性，不能只靠应用层校验。  
  - ⚠️ 易错：验证应在 API 和数据库两层各司其职。
- **索引**：B-tree 常用于查询/排序，加速读取但会增加写入和存储成本。  
  - ⚠️ 易错：不能为每个字段机械地建索引。
- **事务**：BEGIN/COMMIT/ROLLBACK 保证一组操作一致完成或回滚；理解原子性、隔离级别的基本含义。  
  - ⚠️ 易错：多次 SQL 请求在没有事务时不一定是整体操作。

**掌握验收**：
- [ ] 能建 problems 表
- [ ] 会写 4 类 SQL
- [ ] 知道 WHERE 防误操作
- [ ] 能稳定排序与分页
- [ ] 能解释约束和事务

**练习**：使用 PostgreSQL 建表，插入 10 条练习题，再做状态修改、筛选、排序、删除。
**通过标准**：重启数据库服务后数据仍在；违反约束的 INSERT 被拒绝；SQL 文件纳入 Git。

### M11 database/sql 连接 PostgreSQL
- 阶段：数据库 / 第 2 周 / 必学 / 约 4.5h
- **本章目标**：让 Go API 真的读写数据库，而不是用内存假装“后端开发完成”。

- **标准库与驱动**：database/sql 提供接口与连接池，PostgreSQL 要安装相应驱动，例如 pgx/v5/stdlib。  
  - ⚠️ 易错：database/sql 本身不是数据库驱动。
- **sql.Open 与 PingContext**：sql.Open 创建 DB handle，不保证马上连接成功；使用 PingContext 验证可访问。  
  - ⚠️ 易错：错误的地址和密码应在启动时尽快反馈。
- **QueryRowContext**：查询一条记录后 Scan；查询不到行会在 Scan 时得到 sql.ErrNoRows。  
  - ⚠️ 易错：不检查 ErrNoRows 就可能错误返回 500。
- **QueryContext 与 rows**：遍历 rows.Next()，逐行 Scan；defer rows.Close()，循环后检查 rows.Err()。  
  - ⚠️ 易错：只检查 QueryContext 的 err 还不足以发现遍历过程中的错误。
- **ExecContext 与 RETURNING**：UPDATE/DELETE 可通过 RowsAffected 判断是否修改了记录；PostgreSQL 的 INSERT ... RETURNING id 可返回新 ID。  
  - ⚠️ 易错：不同数据库对 LastInsertId 的支持不同，Postgres 通常用 RETURNING。
- **SQL 参数绑定**：PostgreSQL 使用 $1、$2 等占位符，参数单独传入；绝不 fmt.Sprintf 拼接用户值。  
  - ⚠️ 易错：拼接 SQL 可产生注入漏洞，尤其是来自 URL/Body 的内容。
- **连接池与超时**：*sql.DB 是并发安全的连接池句柄；设置 MaxOpenConns、MaxIdleConns，并给请求设置 context 超时。  
  - ⚠️ 易错：不要在每个请求里重新 sql.Open 一个连接池。

**掌握验收**：
- [ ] 能独立连数据库
- [ ] 能插入并获取 id
- [ ] 能正确处理查不到
- [ ] 能用参数化查询
- [ ] 能释放 rows
- [ ] 会设置超时

**练习**：将刷题 API 的内存存储替换为 PostgreSQL；添加两次后重启 Go 服务，记录仍在。
**通过标准**：所有 CRUD 持久化、非法 ID 返回 400/404，SQL 没有字符串拼接输入；数据库不可用时返回合理服务端错误并记录日志。

### M12 测试：单元、HTTP、集成
- 阶段：工程 / 第 3 周 / 必学 / 约 4h
- **本章目标**：从“我点击过看起来能跑”进阶到“我能证明具体需求被满足”。

- **单元测试**：*_test.go + testing.T；使用表驱动测试组织多输入场景，断言结果与预期。  
  - ⚠️ 易错：测试不能自己调用实现重新计算“期望值”，否则同错同对。
- **httptest**：httptest.NewRequest 与 NewRecorder 测 handler，检查 Code、Header 和 JSON。  
  - ⚠️ 易错：只断言状态码 200，可能漏掉响应内容错误。
- **正常/边界/异常**：每个 API 覆盖正常、非法输入、资源不存在、数据库错误；先挑高风险路径。  
  - ⚠️ 易错：只有 happy path 不算有效的后端测试。
- **mock / fake**：用小接口隔离数据库依赖，写可控 fake repository；初学不必引入复杂 mock 框架。  
  - ⚠️ 易错：测试替身的行为也要有明确规则。
- **集成测试**：真实 PostgreSQL 测 SQL、扫描、事务与约束；使用测试库，准备与清理数据。  
  - ⚠️ 易错：单元测试通过不证明 SQL 与数据库能实际工作。
- **race 检测**：go test -race ./... 检查测试覆盖路径中的数据竞争；并发程序尤其重要。  
  - ⚠️ 易错：-race 通过只说明已执行路径未检测到竞争，不代表绝对无线程问题。
- **质量门禁**：go fmt ./...、go vet ./...、go test ./...；有 CI 后让每次提交自动运行。  
  - ⚠️ 易错：测试通过不证明产品需求、权限边界和性能都正确。

**掌握验收**：
- [ ] 能写表驱动测试
- [ ] 会 httptest
- [ ] 会运行 -race
- [ ] 能为错误请求写断言
- [ ] 能解释单元测试和集成测试的区别

**练习**：为 Create/List/Get/Delete 增加自动化测试，故意制造一个 BUG，确认某项测试能够报错。
**通过标准**：至少 12 个有意义的测试场景；数据库相关集成测试与纯函数测试分层；CI/本地运行明确。

### M13 代码结构、配置与日志
- 阶段：工程 / 第 3 周 / 必学 / 约 3.5h
- **本章目标**：让代码可继续增加功能，而不是所有逻辑塞在 main.go 中。

- **按职责拆分**：handler 处理 HTTP，service 处理业务规则，repository 处理数据读写；小项目不必硬拆三层。  
  - ⚠️ 易错：目录变多不等于架构更好；只在复杂度需要时拆分。
- **依赖注入**：用构造函数将 Store/DB 传入 handler，避免到处访问全局变量，测试更容易。  
  - ⚠️ 易错：不要一开始引入复杂 DI 容器。
- **配置项**：PORT、DATABASE_URL 从环境变量读取；本地可以用未提交的 .env。  
  - ⚠️ 易错：密码绝对不要硬编码、提交到 Git 或输出日志。
- **slog 结构化日志**：记录事件、耗时、错误关联信息；客户端返回概括性错误，服务端保留排查细节。  
  - ⚠️ 易错：不要记录密码、token、完整敏感请求体。
- **统一响应与错误映射**：业务错误转换为 HTTP 状态码，例如 ErrNotFound→404、ErrConflict→409。  
  - ⚠️ 易错：不要在 repository 层直接写 HTTP ResponseWriter。
- **README 交付**：写清环境、数据库迁移、启动、调用示例、测试、常见问题；确保另一台机器可以复现。  
  - ⚠️ 易错：只有截图、没有启动步骤的仓库还称不上可交付项目。

**掌握验收**：
- [ ] 能描述各层职责
- [ ] 能通过环境变量启动
- [ ] 不泄漏凭据
- [ ] 有基本日志
- [ ] README 能让别人复现

**练习**：将 CRUD 代码拆成少量职责明确的文件，使用 DATABASE_URL 配置数据库，并写 README。
**通过标准**：自己删除构建产物后依照 README 重来一遍；不会因为遗漏环境变量发生静默错误。

### M14 认证、鉴权与 Web 安全
- 阶段：进阶 / 第 4 周 / 项目必学 / 约 4h
- **本章目标**：在理解普通 CRUD 后，再给项目添加用户账号并保护私人数据。

- **认证 vs 鉴权**：认证（Authentication）确认“是谁”；鉴权（Authorization）判断“能操作哪些资源”。  
  - ⚠️ 易错：登录成功不代表可以访问所有用户的数据。
- **密码处理**：使用成熟密码哈希算法（例如 Argon2id/bcrypt 的可信实现），存哈希不存明文；比较时用库提供的安全方法。  
  - ⚠️ 易错：SHA256(password) 或简单加盐哈希不适合存储用户密码。
- **Session 与 JWT**：Session 通常服务端存状态；JWT 是签名 token，不能因为解码出用户 ID 就信任它，必须校验签名、算法、有效期、签发方等。  
  - ⚠️ 易错：不要将 JWT 理解成天然加密或无需撤销策略。
- **Cookie 属性**：HttpOnly、Secure、SameSite 帮助降低部分风险；基于 Cookie 的状态改变请求需要考虑 CSRF。  
  - ⚠️ 易错：只设置 HttpOnly 并不能解决所有 XSS/CSRF 问题。
- **对象级权限**：例如 GET /problems/{id} 必须检查该题目属于当前用户，不只是要求登录。  
  - ⚠️ 易错：这是初学后端非常容易漏掉的越权问题。
- **SQL 注入、XSS 与 CORS**：SQL 参数绑定；输出到 HTML 时正确转义；CORS 只是浏览器跨源访问策略，不是认证与鉴权。  
  - ⚠️ 易错：开放所有 Origin、把 Token 放 URL 都可能制造问题。
- **速率限制和安全边界**：对登录、注册等接口控制频率；限制 Body 大小；使用 HTTPS；按最小权限运行和连接数据库。  
  - ⚠️ 易错：本地练习可简化，但公网暴露前要建立基本安全措施。

**掌握验收**：
- [ ] 能区分认证和鉴权
- [ ] 密码不会明文保存
- [ ] 会阻止跨用户访问
- [ ] 理解 Cookie/JWT 取舍
- [ ] 能解释 CORS 不是权限

**练习**：给刷题记录增加账户，用户 A 登录后不能读取/修改用户 B 的题目。
**通过标准**：用户密码只存安全哈希；未登录与越权有不同响应；完成至少 2 个越权用例测试。

### M15 并发、context 与优雅退出
- 阶段：进阶 / 第 4 周 / 项目必学 / 约 3.5h
- **本章目标**：理解 Go 后端的并发运行环境，并让取消、超时、共享数据有明确行为。

- **goroutine**：用 go f() 启动并发任务，调度由运行时负责；HTTP server 会并发服务请求。  
  - ⚠️ 易错：创建 goroutine 不等于它可以无限运行或自动处理返回结果。
- **channel**：用于 goroutine 间通信；理解发送/接收、缓冲、有无发送者时的阻塞。  
  - ⚠️ 易错：不要为了使用高级语法而给每次数据库查询都包一层 channel。
- **Mutex 与 RWMutex**：保护共享可变内存；并发 map 读写需要同步，数据库连接池本身可并发使用。  
  - ⚠️ 易错：锁的范围太大可能严重拖慢吞吐。
- **context**：请求上下文传递取消信号/截止时间，数据库与外部 HTTP 调用接受 ctx。  
  - ⚠️ 易错：不要把 context 当作装载所有业务数据的万能 map。
- **超时与资源释放**：context.WithTimeout 和 defer cancel()；避免请求已取消仍无止境运行。  
  - ⚠️ 易错：忘记 cancel 可能延迟资源回收。
- **优雅退出**：接收关闭信号后使用 http.Server.Shutdown(ctx)，给正在进行的请求收尾机会。  
  - ⚠️ 易错：直接 os.Exit 可能中断未完成的请求或日志写入。

**掌握验收**：
- [ ] 能解释 goroutine 和线程关系
- [ ] 能用 mutex 保护数据
- [ ] 会将 ctx 传到 DB
- [ ] 会使用 go test -race
- [ ] 能实现基础优雅退出

**练习**：给 API 加数据库 2 秒超时；模拟慢操作，确认客户端取消可传递；压测并发读取。
**通过标准**：超时可以结束，服务退出不强制丢弃已有请求；-race 在测试覆盖路径中没有发现竞争。

### M17 Gin、ORM、缓存与微服务：何时才学
- 阶段：扩展 / 第 5 周以后 / 延后学习 / 约 按需
- **本章目标**：把框架看作提高效率的工具，而不是替代 HTTP、SQL 和测试基础的捷径。

- **Gin**：路由、绑定、middleware 等更方便；先做过标准库 API 再迁移，才能知道框架在替你做什么。  
  - ⚠️ 易错：直接照抄脚手架会掩盖请求数据流。
- **GORM / sqlc**：ORM 可以减少部分样板 SQL，sqlc 可以从 SQL 生成类型安全代码；理解索引、事务与查询仍必要。  
  - ⚠️ 易错：ORM 不会自动解决 N+1 查询、不合理索引或错误事务边界。
- **Redis 与缓存**：适合热点/会话/限流等场景，核心是键过期、一致性与失效策略。  
  - ⚠️ 易错：用户少、查询快的小项目先不需要 Redis。
- **队列与微服务**：任务异步化、服务拆分需解决幂等、重试、观测、部署复杂度，属于项目确有瓶颈后的选择。  
  - ⚠️ 易错：为了“技术栈高级”而拆微服务常增加维护成本。

**掌握验收**：
- [ ] 知道 Gin 是 HTTP 框架
- [ ] 能用原生 net/http 判断框架抽象
- [ ] 了解 ORM 不替代 SQL
- [ ] 知道何时不该引入 Redis/微服务

### Day 01｜装好 Go，跑通项目

**今天为什么学**：写后端之前，先弄清楚“代码在哪里运行”和“一个 Go 项目如何组织”。今天不背大量语法，只要自己创建、运行、构建一次程序。

#### 知识点与任务的对应关系

- **Go SDK、PATH、编辑器** → 让终端能找到 `go` 命令。`go version` 报“找不到命令”一般是安装或 PATH 问题，和你的代码无关。VS Code 装官方 Go 扩展即可。
- **`package main` 与 `func main()`** → `package` 表示代码所属的包；可执行 Go 程序要有 `main` 包及程序入口 `main()`，对应 C++ 的 `int main()`。
- **`import` 与标准库** → `fmt` 用来格式化输出，`os` 可读环境、参数。Go 的 `import` 引入包，不是 C++ `#include` 那种文本包含。
- **`go.mod` 与模块** → 一个模块可能包含多个包。`go mod init example/go-lab` 创建模块声明；不需要每新建一个 `.go` 文件都初始化。
- **`go run .` / `go build .`** → 前者编译并运行，后者生成可执行文件；`.` 表示当前包，能包含同包的多个 Go 源文件。

#### 可直接运行的示例：`main.go`

```go
package main

import "fmt"

func main() {

    fmt.Println("Hello,", name)
    fmt.Println("目标：28 天写出刷题记录 API")
}
```

**读懂它**：Go 不要求写分号；局部变量用 `:=` 是编译器推断类型；`fmt.Println` 中的 `fmt` 是包名、`Println` 是该包导出的函数。大写开头通常表示标识符可被其他包访问。

#### 跟着做（PowerShell）

### Day 02｜用 Go 重写熟悉的 C++ 题

**今天为什么学**：你已懂循环、条件和函数，不必重新学习“什么是循环”，重点掌握 Go 的写法及与 C++ 的差异。

#### 知识点与任务的对应关系

- **变量与类型** → `var n int = 3` 和 `n := 3` 都能声明变量，`:=` 只允许在函数内；`int`、`int64`、`float64` 之间多数情况下要显式转换。
- **零值** → `var n int` 默认是 `0`，`var ok bool` 默认是 `false`；不要以为 Go 的未赋值变量就是随机垃圾值。
- **`if` / `switch`** → 条件不加圆括号；`switch` 的 `case` 默认不穿透，通常不写 `break`。
- **只有 `for`** → `for i := 0; i < n; i++`、`for condition`、`for {}`；Go 没有 `while` 关键字。
- **函数与多返回值** → `func solve(a, b int) (int, int)` 可以同时返回两个结果；Go 的 `++` 是语句，不是能赋值的表达式。
- **输入输出** → 小练习用 `fmt.Fscan` / `fmt.Fprintln`；算法比赛大量输入时再了解 `bufio.NewReader`、`bufio.NewWriter`。

#### 可直接运行的示例：`main.go`

```go
package main

import (
    "bufio"
    "fmt"
    "os"
)

func calc(a, b int) (int, int) {
    return a + b, a * b
}

func main() {
    in := bufio.NewReader(os.Stdin)
    out := bufio.NewWriter(os.Stdout)
    defer out.Flush()
    var n int
    if _, err := fmt.Fscan(in, &n); err != nil { return }
    sum := 0
    for i := 0; i < n; i++ {
        var x int
        if _, err := fmt.Fscan(in, &x); err != nil { return }
        if x > 0 { sum += x }
    }
    a, b := calc(sum, 2)
    fmt.Fprintln(out, a, b)
}
```

**拆解**：`&n` 把变量地址交给扫描函数，类似 C++ 的引用输入；`a, b := calc(...)` 接住两个返回值；`defer out.Flush()` 在 `main` 返回时刷新缓冲区。`err` 不是异常，而是函数返回的一部分，Day 5 会系统讲。

#### 跟着做

1. 任选三个熟悉的 C++ 小题（求和、最大值、判断回文等），先自己写 Go 版本，再对照输入输出。
2. 把一个 `while` 循环改成 Go 的 `for condition`；把一个 C++ `switch` 改写，并观察是否需要 `break`。
3. 用 `int64` 保存可能超过 32 位的结果；试验 `int64(n)` 强制转换。

**验收样例**：输入 `5` 和 `1 -2 3 0 4`，正数之和是 8，`calc(8,2)` 返回 `8+2` 和 `8*2`，预期输出 **`10 16`**。先手算，再运行程序核对。

**易错提醒**：不要照搬 `cin >> n`、`vector<int>` 或 `a++` 出现在表达式里的 C++ 写法；如果编译器提示变量未使用，先检查代码而不是删除所有提示。

### Day 03｜slice、map、字符串与稳定排序

**今天为什么学**：后端中“列表”“按 ID 索引”“按次数统计”非常频繁；你熟悉的 `vector` 和 `unordered_map`，在 Go 中主要对应 `slice` 和 `map`。

#### 知识点与任务的对应关系

- **数组 vs 切片** → `[3]int` 是固定长度数组，`[]int` 是 slice；slice 有 `len`（当前长度）和 `cap`（容量）。
- **`append`** → `items = append(items, x)` 必须接住返回的 slice；扩容时可能更换底层数组。
- **`map` 与 `make`** → `counts := make(map[string]int)` 可以安全写入；`var m map[string]int` 得到 nil map，能读不能写。
- **`range`** → `for i, v := range xs` 每次给的是元素值；`v = ...` 不会修改原 slice，要写 `xs[i] = ...`。
- **字符串与 Unicode** → `len(s)` 返回字节数，中文字符个数可用 `utf8.RuneCountInString(s)`；`strings.Fields` 按空白字符分词。
- **排序** → `sort.Slice` 自定义排序规则；`map` 的遍历顺序不稳定，输出排名必须显式排序。

#### 可直接运行的示例：`main.go`

```go
package main

import (
    "fmt"
    "sort"
    "strings"
    "unicode/utf8"
)

type Pair struct { Word string; Count int }

func main() {
    text := "Go go Cpp go CPP"
    counts := make(map[string]int)
    for _, word := range strings.Fields(strings.ToLower(text)) {
        counts[word]++
    }
    var list []Pair
    for word, count := range counts {
        list = append(list, Pair{word, count})
    }
    sort.Slice(list, func(i, j int) bool {
        if list[i].Count != list[j].Count { return list[i].Count > list[j].Count }
        return list[i].Word < list[j].Word
    })
    fmt.Println(list) // [{go 3} {cpp 2}]
    fmt.Println(len("中文"), utf8.RuneCountInString("中文")) // 6 2
}
```

**拆解**：`counts[word]++` 读取不存在的键会得到 `int` 的零值，因此词频可以直接累加；排序先比较频次、再比较单词，才能在频次相同时稳定输出。`sort.Slice` 的比较器回答“下标 i 的元素是否排在 j 前面”。

#### 练习与验收

1. 把固定字符串改为用户输入，输出词频 Top 3（不足 3 项就全部输出）。
2. 测试空行、大小写混合、次数并列、中文文本；对中文分词先限定按空白划分，不要求自然语言分词。
3. 做一个 slice 共享实验：`b := a[:2]` 后改 `b[0]`，观察 `a[0]` 是否改变；接着用 `append([]int(nil), a...)` 制造独立副本。

**过关标准**：能解释为什么结果不能直接按 `range map` 的顺序输出；能解释 `len("中")` 为什么是 3。

### Day 04｜struct、指针与方法：不需要先补 C++ OOP

**今天为什么学**：后端要表达“题目”“用户”这样的数据对象。Go 无传统 `class` 和继承语法，用结构体、方法及小接口组织程序。

#### 知识点与任务的对应关系

- **`struct`** → 把字段组合为一个类型，类似 C++ 的结构体；用 `Problem{ID: 1, Title: "..."}` 初始化。
- **方法接收者（receiver）** → `func (p Problem) IsSolved() bool` 表示这个方法作用在 `Problem` 类型上，不必引入 class。
- **值接收者 vs 指针接收者** → `(p Problem)` 得到拷贝；`(p *Problem)` 能修改原对象。指针不是“总是更快”，也要看方法语义。
- **`&` 与 `*`** → `&p` 取地址，`*p` 解引用；Go 用垃圾回收管理普通内存，不需要手写 `delete`。
- **导出规则与 JSON** → `Title` 是导出字段，`title` 通常仅包内可见；JSON 编码器无法通过 `json` tag 强行导出小写字段。
- **接口的第一印象** → 接口描述“具有哪些方法”，类型不需要写 `implements`；**今天只认识，不要求抽象接口体系**。

#### 可直接运行的示例：`main.go`

```go
package main

import (
    "encoding/json"
    "fmt"
)

type Problem struct {
    ID     int64  `json:"id"`
    Title  string `json:"title"`
    Solved bool   `json:"solved"`
}

func (p *Problem) MarkSolved() { p.Solved = true }
func (p Problem) IsSolved() bool { return p.Solved }
func (p Problem) WrongChange() { p.Solved = false } // 仅修改副本

func main() {
    p := Problem{ID: 1, Title: "Two Sum"}
    p.MarkSolved()
    p.WrongChange()
    data, err := json.Marshal(p)
    if err != nil { panic(err) }
    fmt.Println(p.IsSolved(), string(data))
}
```

**拆解**：`p.MarkSolved()` 可写成看似对象调用的方法；Go 会按规则取得地址，使指针接收者方法修改原对象；`WrongChange` 的修改丢失是因为接收者拷贝。这里的 `panic` 只为展示不可预期的内部错误，不应拿来响应无效用户输入。

#### 练习与验收

1. 给 `Problem` 增加 `Platform`、`Difficulty`、`CreatedAt`，只修改代码对应的字段。
2. 写 `Rename(newTitle string)` 和 `MarkUnsolved()`，其中修改原对象的方法使用指针接收者。
3. 定义 `[]Problem`，根据标题关键字筛选，再编码为 JSON。

**过关标准**：自己能讲清楚结构体、方法、接口分别做什么；当方法改不了原对象时，第一时间想到检查值/指针接收者。

### Day 05｜error、defer、JSON：处理外部输入

**今天为什么学**：后端面向不可控输入。一个请求里的字段可能缺失、类型错误或业务无效；Go 的思路是明确返回并处理 `error`。

#### 知识点与任务的对应关系

- **`error` 是普通返回值** → `func parse(...) (Problem,error)`；成功时 `err == nil`，失败时携带原因，通常立即 `return`。
- **错误包装** → `fmt.Errorf("decode request: %w", err)` 能保留底层错误，`errors.Is` 可判断已知错误。
- **`defer`** → 函数返回时执行清理，如 `defer file.Close()` 或 `defer rows.Close()`；不是离开 `if` 就立即执行。
- **JSON 与字段标签** → `json.Unmarshal` 把字节解码到结构体；`json.Marshal` 生成 JSON；`json:"title"` 控制字段名。
- **语法有效 ≠ 业务有效** → `{ "title": "" }` 是合法 JSON，但对新建题目来说无效；需要 `strings.TrimSpace` 再校验。
- **严格解码** → `DisallowUnknownFields` 拒绝未知字段；解码一次后再判断 EOF，以免悄悄接受两个连续对象。

#### 可直接运行的示例：`main.go`

```go
package main

import (
    "encoding/json"
    "fmt"
    "io"
    "strings"
)

type CreateProblem struct { Title string `json:"title"` }

func parse(s string) (CreateProblem, error) {
    dec := json.NewDecoder(strings.NewReader(s))
    dec.DisallowUnknownFields()
    var p CreateProblem
    if err := dec.Decode(&p); err != nil { return p, fmt.Errorf("decode: %w", err) }
    if err := dec.Decode(new(any)); err != io.EOF { return p, fmt.Errorf("expected one JSON object") }
    if strings.TrimSpace(p.Title) == "" { return p, fmt.Errorf("title required") }
    return p, nil
}

func main() {
    for _, input := range []string{`{"title":"Two Sum"}`, `{"title":" "}`, `{"title":10}`} {
        p, err := parse(input)
        fmt.Printf("%+v, error=%v\n", p, err)
    }
}
```

**拆解**：`Decode(&p)` 把 JSON 写入目标结构体，所以传的是地址；JSON 字段类型错了会返回错误；业务非法必须另写校验。用 `err != io.EOF` 判断第二次解码是一种演示写法：真实项目还要区分第二次解码失败与多值输入，以便给出精确响应。

#### 练习与验收

1. 让输入来自标准输入或文件，解析成功后输出标准化 JSON。
2. 增加字段 `platform`，限定非空；试验缺失字段、拼错字段、错误类型和连续两个 JSON 对象。
3. 写 `validateTitle` 函数，让错误原因既能打印出来又能被调用者处理；额外试验一次 `defer` 关闭文件。

**过关标准**：能区分“JSON 解码失败”和“字段值不符合业务规则”；正常错误不要直接 `panic`。

### Day 06｜package、模块与最小自动化测试

**今天为什么学**：单文件练习可以快速上手，但真正项目需要拆包和反复回归。第一条规则是“函数可测试、编译器可检查、项目可复现”。

- **`module` vs `package`** → `go.mod` 定义模块路径，同目录源文件一般归同一个包；`import "example/go-lab/calc"` 引入子目录包。

`calc/math.go`：

```go
package calc

func Add(a, b int) int { return a + b }
```

```go
package calc

import "testing"

func TestAdd(t *testing.T) {
```

```go

    "example/go-lab/calc"
```

### Day 07｜第一个 HTTP 后端：请求怎样变成响应

**今天为什么学**：从今天起，你写的程序不再是“运行一次结束”，而是长期监听端口，等待客户端通过 HTTP 调用。

#### 知识点与任务的对应关系

- **客户端—服务器** → 浏览器/`curl` 发请求，Go 服务接收后选择 Handler，构造状态码、Header、Body 返回。
- **URL 结构** → `http://localhost:8080/add?a=1&b=2`：`8080` 是端口，`/add` 是路径，`?a=1&b=2` 是查询参数。
- **`http.HandlerFunc`** → 函数签名 `func(w http.ResponseWriter, r *http.Request)`；`r` 是输入，`w` 是输出。
- **`ServeMux`** → 标准库路由器，注册方法与路径，例如 `GET /health`。Go 1.22 及更高版本支持这种路由模式。
- **状态码与 Content-Type** → 成功常用 `200`，输入错误用 `400`，内部故障才使用 `500`。响应 JSON 时设置 `application/json`。
- **类型转换与校验** → Query 参数全部是字符串，调用 `strconv.Atoi` 转换，失败应立即返回 400。

#### 可直接运行：`main.go`

```go
package main

import (
    "encoding/json"
    "log"
    "net/http"
    "strconv"
)

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
    })
    mux.HandleFunc("GET /hello", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]string{"message": "hello Go"})
    })
    mux.HandleFunc("GET /add", func(w http.ResponseWriter, r *http.Request) {
        q := r.URL.Query()
        a, e1 := strconv.Atoi(q.Get("a"))
        b, e2 := strconv.Atoi(q.Get("b"))
        if e1 != nil || e2 != nil || !q.Has("a") || !q.Has("b") {
            http.Error(w, "a and b must be integers", http.StatusBadRequest)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]int{"sum": a + b})
    })
    log.Println("listening on http://localhost:8080")
    log.Fatal(http.ListenAndServe(":8080", mux))
}
```

#### 实际发请求（Windows PowerShell）

```powershell
go run .
# 另开一个 PowerShell 窗口：
curl.exe -i "http://localhost:8080/health"
curl.exe -i "http://localhost:8080/add?a=10&b=20"
curl.exe -i "http://localhost:8080/add?a=abc&b=20"
```

**验收**：第二个请求 JSON 中有 `"sum":30`；第三个请求的 HTTP 状态为 `400`，服务不退出。试着只传 `a`、使用负数、让 `b=0`，并解释每一种返回。

**调试提示**：PowerShell 中 `curl` 有时是其他命令的别名，练习时优先使用 `curl.exe`；`&` 必须和整个 URL 一起用双引号包起来。

### Day 08｜先设计 API：URL、REST 与请求契约

**今天为什么学**：直接写代码很容易变成“想到哪个接口就加哪个接口”。今天先明确：客户端发送什么、后端负责什么、成功/失败各返回什么。

#### 知识点与任务的对应关系

- **资源（resource）** → 一条刷题记录是 `Problem` 资源，而不是一个 `doAddProblem` 动作；对外路径用复数名词 `/problems`。
- **HTTP 方法语义** → `GET` 查、`POST` 新增、`PATCH` 改部分字段、`DELETE` 删；不能把所有动作塞进 `GET`。
- **路径参数 vs Query vs Body** → `/problems/12` 指定资源 ID；`?page=2` 控制列表查询；JSON Body 携带要创建/修改的数据。
- **状态码** → 列表/单条成功一般 200，创建 201，删除且不返回响应体用 204，非法请求 400，不存在 404。
- **输入 DTO（请求结构）** → `CreateProblemRequest` 不让调用者自行决定数据库 ID；响应字段可与数据库内部结构不同。
- **接口契约** → 同一类错误使用相同 JSON 形状，方便后续前端和自动化测试。

#### 先写约定，再写 Go 代码

创建题目的请求：

```http
POST /problems HTTP/1.1
Content-Type: application/json

{"title":"Two Sum","platform":"LeetCode","difficulty":"easy"}
```

成功响应示例：

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id":1,"title":"Two Sum","platform":"LeetCode","difficulty":"easy","solved":false}
```

输入错误时统一输出，例如：

```json
{"error":{"code":"INVALID_INPUT","message":"title must not be empty"}}
```

#### 跟着做

1. 定义 `Problem` 字段：`id`、`title`、`platform`、`difficulty`、`solved`、`created_at`。
2. 列出六个端点：列表、单条、创建、局部修改、删除、健康检查；逐项填请求方法、路径、Body 与响应示例。
3. 明确边界：`title` 去空格后必填；`difficulty` 只能是 `easy` / `medium` / `hard`；列表按 `id` 升序排序。

**验收**：不用先启动服务，也能解释为何 `GET /problems?page=2` 的 `page` 不放 JSON Body 里；解释为何 400 与 500 不能混用。

**思考**：如果 `POST` 被客户端重复发送两次，可能创建两条记录；所以要理解幂等性，暂时不必实现复杂的幂等键。

### Day 09｜实现 GET：路由、路径 ID、JSON 输出

**今天为什么学**：把 Day 8 纸上的接口变成真实可访问的 HTTP 路由，第一步只读数据，不处理数据库和复杂并发。

#### 知识点与任务的对应关系

- **`http.NewServeMux`** → 管理 `GET /problems` 和 `GET /problems/{id}`，由 URL 匹配适当的函数。
- **`r.PathValue("id")`** → Go 1.22+ 路由参数，返回字符串，必须转换为整数并检查正数。
- **`r.URL.Query()`** → `?solved=true` 或 `?page=1` 的值，和路径 ID 的意义不同。
- **`json.NewEncoder(w).Encode(...)`** → 向响应 Body 写 JSON；调用前设置 `Content-Type` 和状态码。
- **`404` 与 `400`** → ID 不是数字是 400；合法 ID 但没有这条数据是 404。
- **数据来源** → 今天可以用只读固定 slice 模拟数据库，等 Day 13 再换成 PostgreSQL。

#### 可直接运行的最小 GET 示例：`main.go`

```go
package main

import (
    "encoding/json"
    "net/http"
    "strconv"
    "log"
)

type Problem struct {
    ID int `json:"id"`
    Title string `json:"title"`
}

func main() {
    data := []Problem{{1, "Two Sum"}, {2, "Binary Search"}}
    mux := http.NewServeMux()
    mux.HandleFunc("GET /problems", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(data)
    })
    mux.HandleFunc("GET /problems/{id}", func(w http.ResponseWriter, r *http.Request) {
        id, err := strconv.Atoi(r.PathValue("id"))
        if err != nil || id <= 0 { http.Error(w, "invalid id", 400); return }
        for _, p := range data {
            if p.ID == id {
                w.Header().Set("Content-Type", "application/json")
                _ = json.NewEncoder(w).Encode(p)
                return
            }
        }
        http.Error(w, "not found", 404)
    })
    log.Fatal(http.ListenAndServe(":8080", mux))
}
```

**拆解**：固定 slice 只读，所以此例不需要锁；从 Day 10 开始有并发写入，就不能再无保护地共享可变 slice/map。示例用简短纯文本错误，正式项目再换成统一 JSON 错误结构。

#### 练习与验收

1. `GET /problems` 返回 JSON 数组；`GET /problems/1` 返回一条记录。
2. `GET /problems/999` 必须返回 `404`；`GET /problems/abc` 与 `/problems/-1` 返回 `400`。
3. 扩展 `?solved=true` 过滤；不合法布尔字符串也返回 `400`。用 `curl.exe -i` 查看真实响应头和状态码。

**过关标准**：你能从输入 URL 画出 `ServeMux → Handler → 读取数据 → Encoder → 响应` 的调用链。

### Day 10｜实现 POST：读取 JSON、验证并创建资源

**今天为什么学**：查询很简单，创建资源必须考虑 Body 不是合法 JSON、字段缺失、字段类型错误、写入并发等问题。

#### 知识点与任务的对应关系

- **`r.Body` 与 Decoder** → 请求 Body 是可读取的流；用 `json.NewDecoder(r.Body).Decode(&req)` 将 JSON 写入结构体。
- **限制请求大小** → `http.MaxBytesReader` 在解析前限制输入规模，避免恶意上传巨大 JSON 使服务失去响应。
- **未知字段** → `DisallowUnknownFields()` 能拒绝拼错的键；之后还要检查业务规则。
- **输入 DTO vs 输出模型** → 创建请求中不允许客户端设置数据库自增 ID，后端生成 ID 后再返回。
- **创建响应** → 成功使用 `201 Created`，设置 `Content-Type`，可根据需要设置 `Location`。
- **并发写入** → 标准 Go HTTP 服务可并发执行 Handler，共享计数器和 map 要有互斥锁。

#### 核心代码示例：在 Day 09 的项目里添加创建处理器

下面是一段**函数级代码**，不是独立的 `main.go`；在你的项目中注册 `mux.HandleFunc("POST /problems", createHandler)`，并为存储增加互斥保护。

```go
// 该函数需要 import: encoding/json, errors, io, net/http, strings
// 假设 Problem 已定义，且通过 store.Create 创建数据。
type CreateProblemRequest struct {
    Title string `json:"title"`
    Platform string `json:"platform"`
}

func createHandler(w http.ResponseWriter, r *http.Request) {
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 最多 1 MiB
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()
    var req CreateProblemRequest
    if err := dec.Decode(&req); err != nil {
        var sizeErr *http.MaxBytesError
        if errors.As(err, &sizeErr) { http.Error(w, "body too large", 413) } else {
            http.Error(w, "invalid JSON", 400)
        }
        return
    }
    if err := dec.Decode(new(any)); err != io.EOF {
        var sizeErr *http.MaxBytesError
        if errors.As(err, &sizeErr) { http.Error(w, "body too large", 413) } else {
            http.Error(w, "expected one JSON object", 400)
        }
        return
    }
    req.Title = strings.TrimSpace(req.Title)
    if req.Title == "" { http.Error(w, "title required", 400); return }
    // TODO: 调用你自己实现的 store.Create(req)，取得数据库生成的 id
    // TODO: 将完整 Problem 编码返回，状态码必须是 201
}
```

**拆解**：第一个 `Decode` 把 JSON 装进请求结构；第二个检查是否只有一个 JSON 值；`TrimSpace` 防止只输入空格。使用 `errors.As` 将请求体过大（413）和 JSON 语法错误（400）区分处理；解析完后仍须检查业务规则。

#### 练习与验收

1. 创建 `CreateProblemRequest`，设计 `title`、`platform`、`difficulty` 三个输入字段，并在服务端生成递增 ID。
2. 为可变存储增加 `sync.Mutex`；客户端不应通过 JSON 直接覆盖已有资源的 ID。
3. 测试：合法 JSON → 201；空标题/未知字段/字段类型错误 → 400；过大 Body → 413。若使用 `http.MaxBytesReader`，用 `errors.As(err, &maxErr)` 区分超限。

**过关标准**：用 POST 新增后，再 GET 列表能看到刚创建的记录；错误请求不能让存储内容改变。

### Day 11｜PATCH、DELETE 与内存数据的并发安全

**今天为什么学**：完成完整 CRUD 之前，必须理解“缺失字段”和“设置为 false”不是同一件事，同时保证多个请求不会并发写坏共享数据。

#### 知识点与任务的对应关系

- **CRUD** → Create/Read/Update/Delete；删除成功后再查询应找不到资源。
- **局部更新** → PATCH 更新请求只带要修改的字段；`Solved *bool` 能区分“没传 solved”和“传了 false”。
- **`sync.RWMutex`** → 多个读取者允许并行，写入时独占；每次 map 访问都要遵守锁规则。
- **原子读改写** → 查出旧对象、修改字段、写回 map 必须在同一把写锁保护下完成。
- **状态码** → 删除已存在对象可返回 204；不存在返回 404。不要向 204 响应追加 JSON Body。
- **请求幂等性** → 同一个 `PATCH {"solved":true}` 重试通常产生相同状态；重复删除时是否 404 是接口契约选择。

#### 核心代码：`MemoryStore`（可放入独立包）

```go
package store

import "sync"

type Problem struct { ID int64; Title string; Solved bool }
type Patch struct { Title *string `json:"title"`; Solved *bool `json:"solved"` }
type MemoryStore struct {
    mu sync.RWMutex
    data map[int64]Problem
}
func New() *MemoryStore { return &MemoryStore{data: make(map[int64]Problem)} }

func (s *MemoryStore) Get(id int64) (Problem, bool) {
    s.mu.RLock()
    defer s.mu.RUnlock()
    p, ok := s.data[id]
    return p, ok
}
func (s *MemoryStore) Patch(id int64, req Patch) (Problem, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    p, ok := s.data[id]
    if !ok { return Problem{}, false }
    if req.Title != nil { p.Title = *req.Title }
    if req.Solved != nil { p.Solved = *req.Solved }
    s.data[id] = p
    return p, true
}
func (s *MemoryStore) Delete(id int64) bool {
    s.mu.Lock()
    defer s.mu.Unlock()
    if _, ok := s.data[id]; !ok { return false }
    delete(s.data, id)
    return true
}
```

**拆解**：`Patch` 的指针字段用于区分未提供与提供零值。`RLock` 是读锁，`Lock` 是写锁；加锁后配套 `defer Unlock`，减少错误路径忘记解锁。上面示范的是存储层代码，HTTP 层需自行补 URL 参数、JSON 解码与状态码。

#### 练习与验收

1. 为 `POST` 补 `MemoryStore.Create`，并让 `GET`、`PATCH`、`DELETE` 都操作同一个 store。
2. 发送 `{"solved":false}` 能把原本 `true` 改为 `false`；发送 `{}` 不应无故清空其他字段。
3. `go test -race ./...` 运行存在并发请求的测试，确认无数据竞争；之后 Day 26 再系统学习竞态条件。

**过关标准**：完整内存 CRUD 可用，但重启程序后数据会丢，这是 Day 12～14 要解决的问题。

### Day 12｜SQL 与 PostgreSQL：把记录真正存下来

**今天为什么学**：内存中的 map 在进程退出后消失。数据库负责持久化、按条件查询，并使用约束防止无效数据入库。

#### 知识点与任务的对应关系

- **表、行、列** → 表可类比一组结构体组成的数据集合；每行代表一条记录，列的类型由数据库约束。
- **主键与自增** → `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` 生成唯一标识；ID 不是排名。
- **类型** → `TEXT`、`BOOLEAN`、`TIMESTAMPTZ`、`BIGINT`；`NULL` 表示缺失/未知，不等于空字符串。
- **四种 SQL** → `INSERT` 新增、`SELECT` 查询、`UPDATE` 修改、`DELETE` 删除；更新/删除不写 `WHERE` 会影响整表。
- **约束** → `NOT NULL`、`CHECK`、`FOREIGN KEY` 可以在数据库层面保护数据，不能只依赖 Go 校验。
- **排序** → 需要可预测输出时写 `ORDER BY id`，不要依赖未定义的默认行顺序。

#### 建表文件：`schema.sql`（适用于 PostgreSQL）

```sql
CREATE TABLE IF NOT EXISTS problems (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL CHECK (length(trim(title)) > 0),
    platform TEXT NOT NULL,
    difficulty TEXT NOT NULL CHECK (difficulty IN ('easy','medium','hard')),
    solved BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO problems (title, platform, difficulty)
VALUES ('Two Sum', 'LeetCode', 'easy');

SELECT id, title, solved FROM problems ORDER BY id;
UPDATE problems SET solved = TRUE WHERE id = 1;
DELETE FROM problems WHERE id = 999;
```

**拆解**：`DEFAULT FALSE` 只在未显式提供字段时设置默认值；`CHECK` 保证难度只在允许集合。`CREATE TABLE IF NOT EXISTS` 适合第一次体验，不等于后续修改表结构所需的正式迁移工具。

#### 跟着做

1. 安装并启动本地 PostgreSQL（或使用一个本地临时容器），创建开发数据库 `problems_dev`。
2. 用 `psql` 或图形客户端执行 `schema.sql`；手动插入至少 10 行，练习 `WHERE`、`ORDER BY`、`LIMIT`。
3. 尝试插入空标题或非法难度，确认数据库会拒绝；停止并重启数据库服务后查询刚插入的数据。

**验收**：能写出 `SELECT * FROM problems WHERE solved = false ORDER BY id LIMIT 10;`，并解释其含义。开始认真区分“数据库服务重启”与“删除整个数据目录/容器 volume”。

### Day 13｜Go 连接数据库：驱动、连接池与参数绑定

**今天为什么学**：`database/sql` 是统一的数据库访问接口，但不能直接理解 PostgreSQL 协议，需要额外的数据库驱动。

#### 知识点与任务的对应关系

- **`database/sql` vs 驱动** → 标准库负责查询接口、事务和连接池；如 `pgx/v5/stdlib` 负责连接 PostgreSQL。
- **`sql.Open`** → 得到一个 `*sql.DB` 连接池句柄，不保证当时已经连接成功；再用 `PingContext` 验证。
- **连接字符串 `DATABASE_URL`** → 配置来自环境变量，不要把真实密码提交 Git。
- **`Context` 与超时** → `context.WithTimeout` 限制数据库操作等待时间，`defer cancel()` 释放资源。
- **参数绑定防注入** → PostgreSQL 使用 `$1`、`$2`，把用户输入作为独立参数传给 Query/Exec；不要拼进 SQL 字符串。
- **`QueryRowContext` 与 `Scan`** → 单条结果写入传入的地址；找不到行时 `Scan` 返回 `sql.ErrNoRows`，不能一概当 500。

#### 可运行的连接演示：`main.go`

先在已有 Go 模块执行 `go get github.com/jackc/pgx/v5/stdlib`，并在 PowerShell 设置本地开发数据库连接串（示例凭据仅用于本机临时环境）。

```go
package main

import (
    "context"
    "database/sql"
    "fmt"
    "log"
    "os"
    "time"

    _ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
    db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
    if err != nil { log.Fatal(err) }
    defer db.Close()
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()
    if err := db.PingContext(ctx); err != nil { log.Fatal(err) }
    var count int
    if err := db.QueryRowContext(ctx, "SELECT COUNT(*) FROM problems").Scan(&count); err != nil {
        log.Fatal(err)
    }
    fmt.Println("problem count:", count)
}
```

PowerShell 设置环境变量：

```powershell
$env:DATABASE_URL = "postgres://app:localpass@localhost:5432/problems_dev?sslmode=disable"
go run .
```

**拆解**：`_ ".../stdlib"` 是只为驱动注册执行初始化；`sql.Open("pgx", ...)` 用注册的驱动名；`*sql.DB` 会管理连接池，**不要每次请求都 `sql.Open`**。示例中的 `sslmode=disable` 仅适用于你控制的本地学习环境，部署时必须按环境配置 TLS。

#### 练习与验收

1. 写 `CreateProblem` 使用 `INSERT ... RETURNING id`；写 `GetProblem` 使用 `QueryRowContext(... WHERE id=$1, id)`。
2. 查询不存在的 ID，检查 `errors.Is(err, sql.ErrNoRows)`，将其交由 HTTP 层映射为 404。
3. 传入带单引号和 SQL 关键字的标题，如 `x' OR 1=1 --`，它应该只是普通字段值；确认 SQL 没有被改变。

**过关标准**：能解释驱动、连接池、QueryRow、Scan 各自做什么，也能说明为什么 SQL 字符串拼接不安全。

### Day 14｜从内存 CRUD 升级为 PostgreSQL CRUD

**今天为什么学**：这是最早能称为“做出一个可用后端”的里程碑。把 Day 11 的内存 store 替换为 SQL，HTTP 接口不需要大改。

#### 知识点与任务的对应关系

- **数据访问层（repository）** → 负责 SQL，与 Handler 的 HTTP 输入输出分开；同一接口可以换底层实现。
- **`QueryContext`** → 查询多行，`rows.Next()` 遍历、`Scan` 读取、`defer rows.Close()` 回收资源，最后检查 `rows.Err()`。
- **`ExecContext`** → 执行更新或删除，使用 `RowsAffected` 判断是否影响了目标数据。
- **`RETURNING`** → PostgreSQL 插入后可 `RETURNING id`，比通用的 `LastInsertId()` 更合适。
- **事务** → 多条 SQL 必须“要么全部成功、要么全部失败”时，用 `BeginTx`、`Commit`、`Rollback`。
- **错误分层** → 存储层将 `sql.ErrNoRows` 等转换为领域错误，HTTP 层选择 404/400/500；不要把数据库内部错误原文直接返回用户。

#### 核心片段：从数据库读取列表

以下代码属于你的 repository 层，**需要 Day 13 的 `db *sql.DB` 与你定义的 `Problem` 类型**。它演示正确的多行读取生命周期。

```go
func ListProblems(ctx context.Context, db *sql.DB) ([]Problem, error) {
    rows, err := db.QueryContext(ctx, `
        SELECT id, title, platform, difficulty, solved
        FROM problems ORDER BY id`)
    if err != nil { return nil, fmt.Errorf("query problems: %w", err) }
    defer rows.Close()
    result := make([]Problem, 0)
    for rows.Next() {
        var p Problem
        if err := rows.Scan(&p.ID, &p.Title, &p.Platform, &p.Difficulty, &p.Solved); err != nil {
            return nil, fmt.Errorf("scan problem: %w", err)
        }
        result = append(result, p)
    }
    if err := rows.Err(); err != nil { return nil, fmt.Errorf("rows: %w", err) }
    return result, nil
}
```

#### 迁移步骤

1. 把内存 `Get/Create/Patch/Delete/List` 改为数据库访问；接口路径、JSON 结构与状态码保持 Day 8 的契约。
2. `GET` 使用 `QueryRowContext` 或 `QueryContext`；`POST` 使用 `INSERT ... RETURNING id`；`PATCH/DELETE` 用 `WHERE id=$1` 和 `RowsAffected`。
3. 执行至少六个 API 端点的正常/非法/不存在测试，重启 Go 进程后再次查询数据。

**验收**：合法数据重启后仍能查到；不存在的 ID 返回 404；原始 SQL 语句始终使用参数绑定；`go test ./...` 与后续新增测试不因更换底层存储而全部失效。

**注意**：第 14 天达到“本地可用 CRUD”即可，不等于已经具备账号隔离、容灾备份和公网安全防护。

### Day 15｜测试纯函数：先让错误能被稳定复现

**今天为什么学**：手工测试只能说明“刚才那一次看起来正确”；自动化测试能在以后每次修改代码时重复检查关键行为。

#### 知识点与任务的对应关系

- **测试文件与函数** → 文件名以 `_test.go` 结尾，函数名 `TestXxx(t *testing.T)`，通过 `go test ./...` 运行。
- **表驱动测试** → 把输入、期望结果写在一张切片里；循环逐个运行，很适合 Go 和你已有的算法竞赛习惯。
- **断言** → `if got != want { t.Errorf(...) }`；失败必须给清楚的“实际值与期望值”。
- **边界值** → 业务通常在空串、最大长度、负数、0、重复值附近出问题，不只测正常输入。
- **错误类型/信息** → 业务规则可以返回明确的 error；更复杂时用 `errors.Is` 或自定义错误码，而不是依赖随意变化的字符串。
- **测试独立性** → 预期结果应该由需求或人工算出，不要调用同一个被测实现计算 `want`。

#### 可直接测试的示例：`validation.go`

```go
package validation

import (
    "errors"
    "strings"
    "unicode/utf8"
)

var ErrTitle = errors.New("title must contain 1..80 characters")

func ValidateTitle(s string) error {
    s = strings.TrimSpace(s)
    n := utf8.RuneCountInString(s)
    if n == 0 || n > 80 { return ErrTitle }
    return nil
}
```

与它放在同一目录的 `validation_test.go`：

```go
package validation

import (
    "errors"
    "strings"
    "testing"
)

func TestValidateTitle(t *testing.T) {
    tests := []struct { name, input string; bad bool }{
        {"normal", "Two Sum", false},
        {"empty", "", true},
        {"spaces", "   ", true},
        {"80 chars", strings.Repeat("a", 80), false},
        {"81 chars", strings.Repeat("a", 81), true},
        {"chinese", "动态规划", false},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := ValidateTitle(tt.input)
            if errors.Is(err, ErrTitle) != tt.bad { t.Fatalf("err=%v, bad=%v", err, tt.bad) }
        })
    }
}
```

**拆解**：`t.Run` 给每个样例单独命名；`errors.Is` 比直接比较错误字符串更稳健；`utf8.RuneCountInString` 按 Unicode 码点数计算，需求如果定义“字节数”则要改回 `len`。

#### 练习与验收

1. 为难度字段写 `ValidateDifficulty`，分别测试 `easy`、`medium`、`hard` 及非法值。
2. 给解析分页参数的函数写正常值、缺失、负数、超大值和非数字测试。
3. 故意修改 `ValidateTitle` 使 81 字符也合法，确认测试会失败，然后还原。

**过关标准**：`go test ./...` 通过，并能解释为什么“测试会失败的演示”与“测试恰好全绿”同样重要。

### Day 16｜HTTP 自动化测试：不仅看 200

**今天为什么学**：后端最常见的错误不只是函数计算错，还有状态码错、响应 JSON 字段缺失、Content-Type 错、错误输入没处理。

#### 知识点与任务的对应关系

- **`httptest.NewRequest`** → 创建一个模拟 HTTP 请求，不需要真的监听端口。
- **`httptest.NewRecorder`** → 捕获处理器的 HTTP 状态码、Header 和 Body。
- **`ServeHTTP`** → 调用路由器处理模拟请求，完整覆盖从路由到响应的链路。
- **JSON 断言** → 解码返回 Body 比较字段值，不要只断言响应含某个单词。
- **测试替身（fake）** → 用可控的内存 store 替代数据库，让接口测试不依赖外部 PostgreSQL。
- **错误矩阵** → 每个端点至少覆盖正常、无效输入、资源不存在，后续再覆盖数据库错误与认证失败。

#### 可直接运行的 HTTP 测试示例

`server.go`：

```go
package server

import (
    "encoding/json"
    "net/http"
)

func Routes() http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]string{"status":"ok"})
    })
    return mux
}
```

`server_test.go`：

```go
package server

import (
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "testing"
)

func TestHealth(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/health", nil)
    rec := httptest.NewRecorder()
    Routes().ServeHTTP(rec, req)
    if rec.Code != 200 { t.Fatalf("status=%d", rec.Code) }
    if got := rec.Header().Get("Content-Type"); got != "application/json" {
        t.Fatalf("content type=%q", got)
    }
    var body struct { Status string `json:"status"` }
    if err := json.Unmarshal(rec.Body.Bytes(), &body); err != nil { t.Fatal(err) }
    if body.Status != "ok" { t.Fatalf("body=%+v", body) }
}
```

#### 练习与验收

1. 为 `GET /problems/{id}` 测试：存在返回 200、非法 ID 返回 400、不存在返回 404。
2. 为 `POST /problems` 测试：成功 201、缺标题 400、JSON 错误 400、未知字段 400。
3. 为 `PATCH`、`DELETE` 增加至少两条测试，累计不少于 8 个独立场景。

**过关标准**：`go test -v ./...` 可重复通过；故意改错状态码、响应 JSON 或业务数据中的任意一项，都有对应测试变红。

### Day 17｜数据库集成测试：证明确实写进 PostgreSQL

**今天为什么学**：fake store 的测试可以证明 HTTP 处理逻辑，但不能证明 SQL 是否正确、表结构是否可用、事务是否真会回滚。

#### 知识点与任务的对应关系

- **单元测试 vs 集成测试** → 单元测试隔离外部依赖；集成测试连接真实 PostgreSQL，核验与数据库之间的行为。
- **独立测试数据库** → 用单独的 `TEST_DATABASE_URL`，**绝不要指向真实业务或有价值的数据**；测试可以插入或回滚。
- **事务与清理** → 单个测试把操作包在事务中，最后 `Rollback`；不同测试也能选择独立 schema / 唯一数据。
- **约束验证** → 应测试空标题、重复唯一键、无效枚举值真的被数据库拒绝。
- **重放一致性** → 同样的测试重复运行应该稳定通过，不依赖某一条恰好存在的旧记录。
- **迁移可复现** → 建表 SQL/迁移脚本要能将一个新空库初始化为测试所需结构。

#### 集成测试代码片段：`repository_integration_test.go`

以下测试**需要预先创建测试数据库并执行 Day 12 的 schema**；驱动与数据库需要实际安装。此代码展示连接和事务的基本用法。

```go
package repository

import (
    "context"
    "database/sql"
    "os"
    "testing"
    _ "github.com/jackc/pgx/v5/stdlib"
)

func TestInsertAndRollback(t *testing.T) {
    dsn := os.Getenv("TEST_DATABASE_URL")
    if dsn == "" { t.Skip("set TEST_DATABASE_URL for integration test") }
    db, err := sql.Open("pgx", dsn)
    if err != nil { t.Fatal(err) }
    defer db.Close()
    ctx := context.Background()
    tx, err := db.BeginTx(ctx, nil)
    if err != nil { t.Fatal(err) }
    defer tx.Rollback()
    var id int64
    err = tx.QueryRowContext(ctx, `INSERT INTO problems
        (title,platform,difficulty) VALUES ($1,$2,$3) RETURNING id`,
        "test-one", "local", "easy").Scan(&id)
    if err != nil { t.Fatal(err) }
    if id <= 0 { t.Fatalf("invalid id: %d", id) }
}
```

**拆解**：事务的回滚会撤销插入的数据，但 PostgreSQL 自增序列可能仍然消耗 ID，不能假设序号连续。`t.Skip` 仅用于明确标记外部测试环境未设置，最终交付前必须在具备数据库的 CI/本地环境实际运行过这些集成测试。

#### 练习与验收

1. 为真实 `Create/Get/Patch/Delete` 各写集成测试，不能只测试裸 SQL 示例。
2. 测试数据库约束：空标题应失败、非法 difficulty 应失败；捕获和分类数据库返回的错误。
3. 连续运行测试两次，确认互不污染，最后查询表中不存在测试数据。

**过关标准**：能指出哪些问题必须连接 PostgreSQL 才能发现；能证明测试不会误伤生产库。

### Day 18｜代码分层：让 main.go 不再承包一切

**今天为什么学**：一个文件塞满路由、校验、SQL 和业务规则，修改一处很容易影响别处。分层不是“目录越多越高级”，而是分清职责。

#### 知识点与任务的对应关系

- **Handler（HTTP 层）** → 读路径/Query/Body、决定 HTTP 状态码、写 JSON；不直接决定复杂业务规则。
- **Service（业务层）** → 验证需求规则、组合操作；如果现在业务很简单，可以暂时没有单独 service 层。
- **Repository（存储层）** → 组织 SQL，不应依赖 `http.ResponseWriter`。
- **依赖注入** → `NewHandler(store)` 接受存储依赖，比在函数里使用全局变量更容易测试。
- **小接口** → 在真正需要替身/多实现的一侧定义 `ProblemStore` 接口，不要给每个类型机械地创建接口。
- **错误归属** → Repository 告诉 Handler “不存在”或“数据库故障”；由 Handler 映射为对应 HTTP 响应。

#### 推荐目录（不需要一次建十几个包）

```text
go-backend/
├── cmd/api/main.go          # 启动和依赖组装
├── internal/httpapi/        # HTTP 路由和 Handler
├── internal/problems/       # Problem 类型、业务规则
├── internal/postgres/       # SQL 查询实现
├── db/schema.sql            # 数据库定义
├── go.mod
└── README.md
```

#### 依赖注入的核心代码片段


**拆解**：Handler 不知道底层是不是 PostgreSQL；测试时可传 FakeStore。Go 的接口通过方法集合隐式实现，不需要像 C++ 那样写 `implements` 或建立复杂继承层级。

#### 练习与验收

1. 把所有路由注册收拢到一个地方；把 SQL 代码移入单独的文件/包。
2. 删除“整个项目只有一个 main.go 里几百行逻辑”的结构，但不要为了好看凭空多建五层抽象。
3. 运行全部 HTTP 与数据库测试，确认对外路径、JSON、状态码不变。

**过关标准**：能解释一次请求从 Handler 到 Repository，再返回响应的全过程；能在不启动数据库的情况下测试 HTTP 层。

### Day 19｜配置与日志：能定位问题才算会维护

**今天为什么学**：同一份代码可能在本地、CI、云服务器运行。如果端口和密码写死在代码里，迁移环境就会混乱，泄露密钥的风险也很高。

#### 知识点与任务的对应关系

- **环境变量** → `os.Getenv("PORT")` 读取设置，数据库连接字符串由 `DATABASE_URL` 提供；Git 仓库只提交 `.env.example`，不提交真实 `.env`。
- **显式校验** → 不能把缺失数据库配置默默当作正常；启动前验证必需项，错误消息指出缺什么。
- **结构化日志** → `log/slog` 用键值形式记录时间、事件、错误等信息，便于搜索和分析。
- **日志不能泄密** → 不输出密码、完整数据库 DSN、Bearer Token 或 Cookie。
- **请求关联** → 可加 request ID，结合 HTTP 方法、路径、状态码定位问题；不要把用户输入全部无过滤地写入日志。
- **启动与退出错误** → 端口占用、数据库不可用都应该有清晰报错，而不是无声失败。

#### 可直接运行的配置与日志示例：`main.go`

```go
package main

import (
    "log/slog"
    "os"
    "strconv"
)

func main() {
    logger := slog.New(slog.NewTextHandler(os.Stdout, nil))
    port := os.Getenv("PORT")
    if port == "" { port = "8080" }
    n, err := strconv.Atoi(port)
    if err != nil || n < 1 || n > 65535 {
        logger.Error("invalid port", "port", port)
        os.Exit(1)
    }
    if os.Getenv("DATABASE_URL") == "" {
        logger.Error("missing required DATABASE_URL")
        os.Exit(1)
    }
    logger.Info("configuration loaded", "port", n) // 不记录密码或 DSN
}
```

**拆解**：端口可以给本地默认值；数据库 URL 如果是必需配置，就在启动前检查。`slog.Info` 的键值结构便于后来接入日志平台，但现在不必安装任何平台。

#### 练习与验收

1. 为 API 引入 `PORT` 和 `DATABASE_URL` 两个配置；缺失或非法时在启动阶段明确反馈。
2. 给每个请求添加包含方法、路径、耗时、状态码的简洁日志，不打印完整请求 Body。
3. 搜索仓库，确保没有提交真实密钥；示例配置单独放在 `.env.example`，并加入适当的 `.gitignore`。

**过关标准**：换端口无需改 Go 源码；当数据库地址错误时，开发者能定位原因；日志不含密码。

### Day 20｜筛选、排序、分页：让列表接口真正可用

**今天为什么学**：数据量变大后，`GET /problems` 一次返回全部内容既难用也浪费流量。分页和稳定排序是后端常见需求。

#### 知识点与任务的对应关系

- **Query 参数** → `?page=2&limit=20&solved=true` 用于列表筛选；不要把它们误认为路径参数。
- **默认值与上限** → 未提供 `page` 默认 1、`limit` 默认 20；限制 `limit` 最大 100，非法值返回 400。
- **OFFSET/LIMIT** → SQL 的 `LIMIT $1 OFFSET $2` 限制返回数量；偏移 `(page-1)*limit`。
- **稳定排序** → `ORDER BY id` 保证同样查询的顺序可预测；没有排序，分页可能重复/遗漏数据。
- **参数化筛选** → `WHERE solved=$1` 的布尔值作为参数传递；排序字段等 SQL 标识符要在白名单里选择，不能直接把用户字符串拼进去。
- **索引及代价** → 索引能加快某些查询，但也占空间并拖慢写入；先了解 `EXPLAIN`，不要见字段就建索引。

#### SQL 与分页换算

```sql
-- 已将 solved、limit、offset 解析并校验后再作为参数传入
SELECT id, title, solved
FROM problems
WHERE solved = $1
ORDER BY id
LIMIT $2 OFFSET $3;
```

Go 中的分页参数检查：

```go
func parsePagination(q url.Values) (page, limit int, err error) {
    page, limit = 1, 20
    if s := q.Get("page"); s != "" {
        page, err = strconv.Atoi(s)
        if err != nil || page < 1 { return 0, 0, fmt.Errorf("invalid page") }
    }
    if s := q.Get("limit"); s != "" {
        limit, err = strconv.Atoi(s)
        if err != nil || limit < 1 || limit > 100 { return 0, 0, fmt.Errorf("invalid limit") }
    }
    if page > 1000000 { return 0, 0, fmt.Errorf("page too large") }
    return page, limit, nil
}
```

**拆解**：`url.Values` 来自 `net/url`，`strconv.Atoi` 和 `fmt.Errorf` 要导入相应包。上面的函数属于一个更大的 Go 包，并非独立程序。`OFFSET` 适合入门和小数据量；数据量巨大时了解基于游标的 keyset pagination。

#### 练习与验收

1. 实现 `GET /problems?page=...&limit=...`，结果带一个可预测的顺序。
2. 增加 `solved=true/false` 过滤；缺失时返回全部，布尔字符串非法时返回 400。
3. 比较 `page=1/2/3`，确认没有重复记录；测试 `limit=0`、`limit=1000`、`page=-1`。

**过关标准**：接口即使有 500 条数据，也能按分页访问，且无 SQL 拼接用户输入。

### Day 22｜认证 vs 鉴权：开始设计多用户数据

**今天为什么学**：没有登录的 CRUD 只是共享记事本。要做真正的个人账户后端，必须区分“用户是谁”和“用户能不能访问这条记录”。

#### 知识点与任务的对应关系

- **认证（Authentication）** → 确认请求来自哪个已登录用户；例如用户提交凭据后建立会话。
- **鉴权（Authorization）** → 即使已经登录，也必须判断是否有权限读取、修改或删除某条资源。
- **用户与资源归属** → `users` 表存账号，`problems.owner_id` 关联用户；每个查询都应限定当前用户。
- **密码存储原则** → **不保存明文或可逆加密的密码**，使用专门的密码哈希算法和唯一随机盐。
- **最小权限** → 认证通过不代表可以访问任意用户 ID；管理员权限是另外设计的问题。
- **统一错误语义** → 未登录为 401；登录但无权访问可选 403，或在资源层统一返回 404 防止暴露资源是否存在。

#### 两张表的关系（用于一个新项目）

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 如果从 Day 12 单用户表迁移：先处理已有记录，
-- 再新增 owner_id、回填数据、设置 NOT NULL 和外键。
ALTER TABLE problems
ADD COLUMN owner_id BIGINT REFERENCES users(id);
```

**拆解**：原本 `problems` 没有 `owner_id`，不能直接假设旧数据已有归属。`ADD COLUMN` 先可空是为了让你有机会处理旧记录，实际部署迁移须按已有数据情况安排。`password_hash` 是文本形式的算法输出，而不是原密码。

#### 练习与验收

1. 在纸上设计两个测试用户 A 和 B，各自拥有两条题目。
2. 写出列表 SQL：`SELECT ... FROM problems WHERE owner_id=$1 ORDER BY id`，说明 `$1` 从**已验证的会话**得来，不是直接信任用户填写的 `owner_id`。
3. 写出“用户 A 查询 B 的题目”的预期结果，决定你的 API 返回 403 还是 404，并保持一致。

**过关标准**：能用自己的话解释“登录成功不等于拥有资源权限”，并能画出 `users.id → problems.owner_id` 的关系。

### Day 23｜注册与登录：密码哈希和会话的基本流程

**今天为什么学**：账号功能是安全敏感的部分。先明确注册、验证密码、建立会话的流程，不靠浏览器传递“我是用户 3”这种不可信信息。

#### 知识点与任务的对应关系

- **注册流程** → 验证邮箱和密码规则 → 对密码做专用哈希 → 保存用户记录；邮箱唯一性要由数据库约束。
- **密码哈希** → 演示使用 `golang.org/x/crypto/bcrypt` 的 `GenerateFromPassword` 与 `CompareHashAndPassword`；密码不放 URL、不写日志。
- **验证密码** → 不存在用户、密码错误都要返回相近的外部错误语义，避免泄露账号存在性。
- **Session（会话）** → 登录成功后产生随机、不可猜测的会话令牌；服务端保存对应的身份与失效时间。
- **Cookie 选项** → `HttpOnly` 防止网页脚本读取 Cookie；正式 HTTPS 场景设置 `Secure`、合适的 `SameSite` 与有效期。
- **限流/暴力尝试防护** → 登录接口尤其需要合理限流、错误次数监控，不要无保护地公开在公网。

#### 可运行的密码哈希演示：`main.go`

先执行 `go get golang.org/x/crypto/bcrypt`（此代码需下载依赖）。

```go
package main

import (
    "fmt"
    "log"
    "golang.org/x/crypto/bcrypt"
)

func main() {
    password := []byte("strong passphrase 123")
    hash, err := bcrypt.GenerateFromPassword(password, bcrypt.DefaultCost)
    if err != nil { log.Fatal(err) }
    fmt.Println("saved hash:", string(hash))
    err = bcrypt.CompareHashAndPassword(hash, password)
    fmt.Println("correct password:", err == nil)
    err = bcrypt.CompareHashAndPassword(hash, []byte("wrong"))
    fmt.Println("wrong password:", err == nil)
}
```

**拆解**：同一密码每次哈希的字符串通常不同，因为包含随机盐；验证不是重新哈希后直接对比文本，而是使用 `CompareHashAndPassword`。bcrypt 有 **72 字节输入长度限制**，真实项目要明确处理过长密码；更深入可比较 Argon2id 的适用性。

#### 练习与验收

1. 实现 `POST /register`：格式校验、邮箱规范化、密码哈希、唯一邮箱冲突处理；响应中**不能出现**密码或哈希。
2. 实现 `POST /login`：按邮箱查哈希并验证，密码正确才建立会话；暂时不接前端页面。
3. 验证数据库中密码不是明文；同一邮箱重复注册返回冲突；密码错误无法登录；Cookie 不在日志中暴露。

**过关标准**：能讲清楚“密码哈希”和“Session Token”是两种完全不同的东西，前者用于验证密码，后者用于标识登录状态。

### Day 24｜把用户身份放进每条 CRUD：防越权

**今天为什么学**：后端安全漏洞经常不是“没人登录就进来”，而是“登录 A 后，通过改 URL 中的 ID 读到了 B 的数据”。

#### 知识点与任务的对应关系

- **可信身份从何而来** → 服务端通过 Session/JWT 的合法性校验得到用户 ID；不能直接信任请求里的 `user_id` 字段。
- **Session vs JWT** → Session 常用随机令牌 + 服务端存储；JWT 是签名令牌，但依旧要验证签名、有效期及适用范围。
- **授权检查** → 每条查询都带 `owner_id` 条件，避免先把别人的数据读出来再决定不显示。
- **对象级鉴权** → 不仅列表要筛选，单条 GET、PATCH、DELETE 也要检查资源归属。
- **401/403/404** → 无有效会话返回 401；无权限访问现有对象时可 403 或 404，保持策略一致。
- **退出与过期** → Session 需要有限有效期；退出时使服务端会话失效。仅删除浏览器 Cookie 不能撤销全部服务端凭据。

#### 关键 SQL：不要仅用资源 ID

```sql
-- 当前用户 ID 必须从已验证的登录会话中获得。
SELECT id, title, solved
FROM problems
WHERE id=$1 AND owner_id=$2;

UPDATE problems SET solved=$1
WHERE id=$2 AND owner_id=$3;

DELETE FROM problems
WHERE id=$1 AND owner_id=$2;
```

安全做法的 Handler 伪代码：

```text
1. 从 Cookie 读取随机会话令牌
2. 服务端查 session、核验过期和撤销状态
3. 查到 userID；失败 → 401
4. 从 PathValue 解析 problemID（错误 → 400）
5. SQL 使用 problemID + userID 双条件查询
6. 查询不到 → 404；成功 → 200
```

**拆解**：若请求来自用户 A，即使修改 URL 为 B 的记录 ID，SQL 也不会返回 B 的数据。这个规则适用于写操作，不能只在 GET 列表上实现。

#### 练习与验收

1. 准备两个账号 A 和 B，各自至少两条记录；逐一验证 A 看不到、改不了、删不了 B 的记录。
2. 清除 Cookie 后尝试 CRUD，必须返回 401；手动伪造 `owner_id` 字段不能改变真实身份。
3. 退出登录，确认之前的会话令牌在服务端已失效，而不是只让浏览器界面显示“退出”。

**过关标准**：能自己写出用户隔离的自动化测试，这是第 24 天比新增页面更重要的交付物。

### Day 25｜后端安全底线：输入、SQL、HTTP、权限

**今天为什么学**：功能越完整，越需要系统检验错误输入、并发和越权。今天不是做“企业级安全系统”，而是补齐几个常见且容易验证的防线。

#### 知识点与任务的对应关系

- **输入验证** → 字段类型、长度、枚举范围、未知 JSON 字段和过大的 Body 都要有明确规则。
- **请求体上限** → `http.MaxBytesReader` 限制 Body，超过限制应返回 413；不要把全部请求直接 `io.ReadAll` 到无限大的内存中。
- **SQL 注入** → 用户数据使用 `$1/$2` 参数绑定；SQL 表名、排序列如需动态选择，必须用固定白名单。
- **CORS** → 浏览器跨源读取响应的安全机制，不是“后端开放 CORS 就自动安全”；不需要跨域就不必随意设置 `*`。
- **CSRF** → Cookie 认证要结合合适的 SameSite 设置、Origin/CSRF 防护；不能只靠登录 Cookie 就认为所有状态修改安全。
- **HTTPS、错误隐藏** → 公网使用 HTTPS；对用户返回稳定错误码，不泄露 SQL、服务器路径、密钥等内部细节。
- **限流** → 登录、注册和高代价查询要有基本限制和监控；单进程内存计数在多实例部署时不够。

#### 识别请求体超限的示例片段

这段代码可用于已经使用 `r.Body` 的 Handler 内，**需要导入** `encoding/json`、`errors`、`net/http`。

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
var input CreateProblemRequest
err := json.NewDecoder(r.Body).Decode(&input)
if err != nil {
    var limitErr *http.MaxBytesError
    if errors.As(err, &limitErr) {
        http.Error(w, "request body too large", http.StatusRequestEntityTooLarge)
    } else {
        http.Error(w, "invalid JSON", http.StatusBadRequest)
    }
    return
}
```

**拆解**：`errors.As` 可以判断包装后的错误类型；不同的客户端错误应该有合理的 4xx 状态，而不是将所有意外都返回 500 或 200。这个片段仅处理解码错误，仍须补业务校验、未知字段和第二个 JSON 对象的检查。

#### 练习与验收

1. 故意发送 2 MiB 请求体、嵌套异常 JSON、拼错的字段、非法难度，检查响应和服务器稳定性。
2. 用包含单引号、SQL 关键词的标题创建记录，再查询它，确认标题被当作文本保存。
3. 测试无登录、过期会话、跨用户访问、非法 `Origin`；检查 HTTP 响应不泄露内部堆栈信息。

**过关标准**：形成一张安全测试表，标清“输入 → 预期状态码 → 实际结果 → 是否修复”，而不是只在报告中写“已考虑安全”。

### Day 26｜Go 并发、context、超时与优雅退出

**今天为什么学**：Go Web 服务在同一时刻可以接收多个请求。如果共享数据操作不加保护，或者关闭服务时直接杀进程，就可能出现竞态和中断。

#### 知识点与任务的对应关系

- **goroutine** → `go f()` 在新的 goroutine 并发执行，不等于每一个都会独占一个系统线程。
- **channel** → goroutine 之间传递数据或同步的一种方式；先了解作用，不要求今天实现复杂 worker pool。
- **`sync.Mutex` / `RWMutex`** → 保护共享可变内存，尤其是第 11 天的 map；并发读写 map 不安全。
- **`context.Context`** → 随请求传递截止时间和取消信号；数据库调用使用 `r.Context()` 或其派生 context。
- **超时** → `context.WithTimeout` 限制慢查询占用资源，函数返回时调用 `cancel()`。
- **优雅退出** → 停止接收新连接，给在途请求留出收尾机会，再关闭数据库连接池。
- **`go test -race`** → 动态检查实际跑到的路径中的数据竞争；检查没报警不等于所有并发问题都不存在。

#### 优雅退出的最小可运行程序：`main.go`

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("ok"))
    })
    srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()
    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Printf("server error: %v", err)
            stop()
        }
    }()
    <-ctx.Done()
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil { log.Printf("shutdown: %v", err) }
}
```

**拆解**：`go func(){ ... }()` 启动一个 goroutine 运行服务器；主 goroutine 等待系统退出信号；`Shutdown` 让 HTTP Server 有机会处理在途请求。这个示例使用 `syscall` 的传统信号常量，适合跨平台理解，实际 Windows/Linux 行为需按环境测试。

#### 练习与验收

1. 为一次耗时数据库查询加 `context.WithTimeout(r.Context(), 2*time.Second)`；观察超时如何传递。
2. 给内存存储写一个并发测试，先故意去掉锁运行 `go test -race`，再恢复锁并检查。
3. 运行 API，发出一个持续几秒的请求，再用 Ctrl+C 退出，查看是否有机会完成请求或在期限内取消。

**过关标准**：能区分“数据竞争”“业务逻辑竞态”“超时取消”三个概念，不再把 goroutine 理解为自动安全。

### Day 27｜Docker 和 Compose：让 API 与数据库一起启动

**今天为什么学**：用户不一定和你装了一样的 Go/数据库版本。容器可以把运行环境固定下来，Compose 帮你一次启动 API 和 PostgreSQL。

#### 知识点与任务的对应关系

- **镜像（image）vs 容器（container）** → 镜像是构建好的运行模板，容器是实际运行的实例；删容器不一定等于删数据卷。
- **Dockerfile 多阶段构建** → 第一阶段用 Go 编译二进制，第二阶段只保留运行所需文件，减小最终镜像。
- **Compose 服务名** → API 连接数据库时使用 `db:5432`，不是容器内的 `localhost:5432`。
- **volume** → 数据库文件存在持久化 volume 中，重启容器数据才不会因为容器的可写层丢失。
- **健康检查与启动顺序** → `depends_on` 本身不总能保证数据库已经可连接；结合 healthcheck 和应用启动重试。
- **配置与密钥** → `.env` 只用于本地开发；正式环境要把数据库密码交给安全配置机制，而不是写进 Dockerfile。

#### `Dockerfile`（假设入口为 `./cmd/api`）

```dockerfile
FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12:nonroot
WORKDIR /
COPY --from=build /out/api /api
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/api"]
```

```yaml
  contents: read
```

## 6. C++ ↔ Go 重点对照

| C++ | Go | 易错点 |
|---|---|---|
| `#include <bits/stdc++.h>` | `import (...)` | 按包引入；没有万能头文件 |
| `int main()` | `func main()` | 可执行代码在 package main |
| `auto x = 3;` | `x := 3` | 短声明只能在函数内部 |
| `vector<int> a;` | `a := []int{}` | 切片不是完整的 C++ vector 复制语义 |
| `a.push_back(x);` | `a = append(a, x)` | 别丢掉 append 的返回值 |
| `unordered_map<string,int>` | `map[string]int` | 写入前 make 初始化 |
| `for (auto &x : a)` | `for i := range a` | 修改 a[i]，range 的 value 是副本 |
| `pair<int,int>` | `struct 或多返回值` | Go 函数可以 return x,y |
| `nullptr` | `nil` | 引用类类型的零值 |
| `string.size()` | `len(s)` | len(string) 返回 UTF-8 字节数 |
| `class / public / private` | `struct + 方法 + 大小写导出` | 没有传统类继承；大写跨包导出 |
| `throw / catch` | `return value, err` | 普通失败走 error，不靠 panic |
| `new / delete` | `&v / new(T) + GC` | 一般无需手动释放内存 |
| `std::mutex` | `sync.Mutex` | 保护共享内存，非数据库连接对象 |
| `std::thread` | `go f()` | 运行时调度，并发先学正确性 |
| `std::optional<T>` | `(T, bool) 或 (T,error)` | 依语义返回存在性或错误 |
| `std::map 有序遍历` | `map 顺序不保证` | 需要稳定顺序自己取 key 排序 |
| `cout / cin` | `fmt / bufio` | Web 开发更常用 HTTP Body 与 JSON |

```go
func parseID(s string) (int64, error) {
```

### ⑤ 直接运行的第一个 HTTP 后端
保存为 main.go：GET /health 和 GET /add?a=3&b=5。

```go
package main

import (
    "encoding/json"
    "log"
    "net/http"
    "strconv"
    "time"
)

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
    })
    mux.HandleFunc("GET /add", func(w http.ResponseWriter, r *http.Request) {
        q := r.URL.Query()
        a, errA := strconv.Atoi(q.Get("a"))
        b, errB := strconv.Atoi(q.Get("b"))
        if errA != nil || errB != nil {
            http.Error(w, "a and b must be integers", http.StatusBadRequest)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(map[string]int{"result": a + b})
    })
    srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}
    log.Fatal(srv.ListenAndServe())
}
```

### ⑥ JSON 请求：解析后还要校验
这是可放进 handler 的代码片段，不是独立 main.go。

```go
type CreateProblemRequest struct {
    Title    string `json:"title"`
    Platform string `json:"platform"`
}

// handler 内：先限制体积，再解码。
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
var req CreateProblemRequest
dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()
if err := dec.Decode(&req); err != nil {
    http.Error(w, "invalid JSON", http.StatusBadRequest)
    return
}
var extra any
if err := dec.Decode(&extra); err != io.EOF {
    http.Error(w, "only one JSON value is allowed", http.StatusBadRequest)
    return
}
if strings.TrimSpace(req.Title) == "" {
    http.Error(w, "title is required", http.StatusBadRequest)
    return
}
```

### ⑦ PostgreSQL 建表和查询

```sql
CREATE TABLE IF NOT EXISTS problems (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL CHECK (length(trim(title)) > 0),
    platform TEXT NOT NULL,
    solved BOOLEAN NOT NULL DEFAULT FALSE,

);

INSERT INTO problems (title, platform)
```

## 8. 14 道自测题（答案）

**Q01 go run . 与 go run main.go 最大区别是什么？**  
- ✅ 前者会运行当前包的全部适用 Go 源文件
- ○ 前者不需要 go.mod
- ○ 前者永远更快
- 解释：项目拆文件之后，用 go run . 能编译当前包所有适用源文件。

**Q02 下面哪种 Go 写法用于在函数内简短声明变量？**  
- ○ int x = 3;
- ✅ x := 3
- ○ auto x = 3
- 解释：Go 的 := 是短变量声明运算符。

**Q03 map[string]int 的零值能直接写入键吗？**  
- ○ 可以，不需要初始化
- ✅ 不可以，通常先 make
- ○ 只有声明全局变量时才可以
- 解释：nil map 可读取，但赋值到 nil map 会 panic。

**Q04 给 struct 的字段赋新值，应优先考虑什么方法？**  
- ○ 值接收者
- ✅ 指针接收者
- ○ 泛型方法
- 解释：指针接收者通常用于改变原对象。

**Q05 用户填写非法题目 ID，最恰当的处理方式？**  
- ○ panic
- ✅ 返回 error 并映射到 400
- ○ 无条件返回 500
- 解释：客户端输入不合法是可预期错误。

**Q06 Go 如何识别包的导出标识符？**  
- ✅ 名字首字母大写
- ○ 名字带 public
- ○ 名字以 _ 开头
- 解释：首字母大写表示该标识符可从其他包访问。

**Q07 GET /problems/{id} 找不到记录通常返回什么状态码？**  
- ○ 201
- ✅ 404
- ○ 500
- 解释：404 表示所请求资源不存在。

**Q08 下面哪个来自请求 URL 的查询参数？**  
- ✅ r.URL.Query().Get("page")
- ○ r.Body.Close()
- ○ w.Header().Set(...)
- 解释：Query 是 URL 问号之后的参数。

**Q09 HTTP 服务有多个请求同时写全局 map 时应做什么？**  
- ○ 什么都不做
- ✅ 用互斥锁/改用安全存储
- ○ 禁用 HTTP/1.1
- 解释：共享 map 并发写可能出现数据竞争或崩溃。

**Q10 查询数据库时为什么必须使用 $1 参数绑定？**  
- ○ 为了提高字体可读性
- ✅ 避免不可信数据改变 SQL 语义
- ○ 保证结果自动排序
- 解释：参数化 SQL 是防 SQL 注入的基本措施。

**Q11 sql.Open("pgx", dsn) 一定说明数据库连通吗？**  
- ○ 是
- ✅ 不是，应 PingContext
- ○ 只要没有 panic 就是
- 解释：sql.Open 一般构造句柄，实际连接可能要等后续操作。

**Q12 自动化测试只验证返回 200 足够吗？**  
- ○ 足够
- ✅ 不够，还要断言响应内容与错误路径
- ○ HTTP 无法测试
- 解释：状态正确但内容错、权限错时仍然可能出现严重问题。

**Q13 把用户 ID 写在路径里且已经登录，就可访问所有 ID 的数据？**  
- ○ 可以
- ✅ 不可以，必须检查资源归属权限
- ○ 只有本地可以
- 解释：用户鉴权必须做到对象/资源级，而不只是检查登录。

**Q14 Go 的 -race 检查结果通过，说明什么？**

## 9. 避坑与 AI 学习策略

- **避免：还没写 HTTP 就上 Gin + GORM**；替代：先用 net/http 和 SQL 跑通链路；之后框架才是加速器。
- **避免：一上来学微服务/K8s/Redis**；替代：单体 CRUD 足够练习真实问题；没有规模问题不必引入。
- **避免：AI 一次写完整项目**；替代：让 AI 解释错误、审阅你的实现；每天至少自己完整写一次核心功能。
- **避免：只做能成功的测试**；替代：故意测非法输入、缺失资源、越权、断连，才知道系统边界。
- **避免：目录层数越多越“企业级”**；替代：按实际职责划分；初学项目 main+handler+store 即可起步。
- **避免：只背语法不做项目**；替代：每学一个知识点马上写可运行的例子；每周保留可演示版本。

每天问自己：数据从哪里进来？流经什么函数？输入错误数据会怎样？不要让 AI 第一次就生成完整项目。

## 10. 后端术语词典

- **API**：应用程序接口；这里通常指前端与服务器沟通的 HTTP 约定。
- **CRUD**：Create/Read/Update/Delete，增删改查。
- **HTTP**：请求—响应协议，方法、路径、状态码、Header、Body 组成一次交互。
- **HTTPS**：HTTP over TLS；网络传输加密并支持服务器身份验证。
- **REST**：一种资源导向的架构风格；关键是明确资源、方法与响应语义。
- **JSON**：文本数据交换格式；Go 主要用 encoding/json。
- **Handler**：接收 HTTP 请求并写响应的处理函数/对象。
- **Middleware**：在最终 Handler 前后执行共同逻辑，如日志、认证等。
- **DTO**：传输数据对象；定义客户端允许提交、接收的字段。
- **Repository**：隔离数据库操作的代码职责，不必一开始就建复杂框架。
- **Module**：以 go.mod 定义依赖和模块路径的项目单元。
- **Package**：Go 源文件的组织与命名空间；目录通常对应一个包。
- **Slice**：动态切片，指向底层数组的一段视图。
- **Interface**：方法集合构成的行为契约；Go 隐式实现。
- **Receiver**：声明方法时绑定到类型的接收者。
- **Pointer receiver**：对接收者指针操作，通常用于修改值或避免复制大对象。
- **Zero value**：变量未显式初始化时对应类型的默认零值。
- **error**：用于返回可预期失败信息的内建接口类型。
- **defer**：安排在当前函数返回时执行的语句。
- **Context**：取消、截止时间和请求范围信号的传递机制。
- **Goroutine**：由 Go 运行时调度的轻量并发执行单元。
- **Mutex**：互斥锁，用来保护共享可变状态。
- **Race condition**：多种执行时序导致结果变化；数据竞争是其中一种具体问题。
- **SQL injection**：把不可信数据拼接进 SQL 文本，令其改变查询含义的漏洞。
- **Migration**：版本化数据库结构变更，使环境可一致重建。
- **Transaction**：保证一组数据库操作以一致方式提交或回滚。
- **Index**：辅助数据库加速查找/排序的结构，存在成本。
- **Authentication**：认证：确认用户身份。
- **Authorization**：鉴权：确认用户对资源/动作的权限。
- **JWT**：签名令牌格式；不能将它误认为加密或自动安全。
- **CORS**：浏览器跨源请求访问控制；不是后端授权机制。
- **CI**：持续集成；每次提交自动运行检查和测试。
- **Docker**：打包与运行容器的工具；和数据库持久化/部署策略分开理解。
